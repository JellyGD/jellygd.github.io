常有这种时刻：想给辅食 App 加个「AI 推荐」，第一反应不是「功能怎么做」，而是「该用哪个框架？」——然后一搜，LangChain、LangGraph、CrewAI、LlamaIndex、Core ML、MLX、Foundation Models……二十多个名字砸过来，越看越慌。

其实这方向本身就慌错了。这些名字看着像竞品，实际是**两层完全不同的东西**被混在一起叫了「框架」。一旦分层，选择立刻变简单——而且会发现早就用上了一层，只是没意识到。

## 先给结论

**「框架」= 两层：**

- 底层是**推理运行时**：模型在手机 / 服务器上怎么加载、跑前向、吐 token；
- 中间层是**编排框架**：agent 怎么思考、怎么调工具、怎么管状态。

我那辅食 App 用的是底层（llama.cpp），练手的订单 demo 用的是中间层（LangChain）。两层各管各的，别再当成一道单选题。

## 第一层：推理运行时——像给播放器选解码器

做视频播放治理时最清楚：同样的视频，走**硬解（VideoToolbox / MediaCodec）**省电但挑格式，走**软解（ffmpeg）**兼容一切但费 CPU。选运行时，就是选「解码器」。

移动端（尤其 iOS）2026 年三条现实路径：

- **llama.cpp（Metal 后端）**：我那辅食 App 用的。开源、兼容几乎所有 GGUF 量化格式，新模型出来当天就能跑。代价是不走 ANE、不是最省电。它的定位就是「软解」——通用、稳。
- **Core ML**：iOS 原生，转得好时最快最省电（能上 ANE）。代价是转换链路脆弱，Meta / Mistral 出新架构往往要等社区适配。这是「硬解」——快，但挑剔。
- **Apple Foundation Models（iOS 26+）**：系统自带、无需下载权重、不用管 KV cache。简单场景直接调，像系统预装了一个「基础播放器」。但有 4096 token 总预算、旧设备必须 fallback。

我那辅食 App 选 llama.cpp，不是「不会用 Core ML」，而是**当时要的是「什么模型都能跑、不被 Apple 转换链路卡住」**——这正是软解的思路。这个选择到现在都站得住。

## 第二层：编排框架——像给网络层选方案

写 iOS 网络层时也都纠结过：用系统 `URLSession` 手写，还是引 `AFNetworking` / `Alamofire`？手写轻、可控；框架省事、功能全。**编排框架也是同一道题。**

- **LangChain**：链式编排，上手最快。那个订单客服 demo 就在这层——把「读消息 → 查订单 → 生成回复」串成链，几分钟跑通。
- **LangGraph**：把 agent 建模成「有状态的状态图」，生产级。支持暂停 / 恢复 / checkpoint、human-in-the-loop、长任务回滚。等 agent 要处理「多步、可能失败、需要重试」的复杂流程再上。
- **CrewAI / AutoGen**：多智能体专用——一个负责查、一个负责写、一个负责审。单 agent 用不上。
- **Pydantic AI / OpenAI Agents SDK**：更轻、类型安全，单 agent 场景比 LangGraph 省心。

这里有个**容易踩的坑**：很多人觉得「用 LangChain 才叫做 Agent」。不是。LangChain 只是在中间层帮写胶水代码，不让模型变聪明，也不管底层推理。

```python
from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate

# 直接指向本地 Ollama，不依赖任何云端
llm = ChatOpenAI(model="qwen2.5:4b", base_url="http://localhost:11434/v1")
prompt = ChatPromptTemplate.from_messages([
    ("system", "你是订单客服，只回答订单相关问题"),
    ("user", "{question}"),
])
chain = prompt | llm
print(chain.invoke({"question": "我的订单到哪了？"}))
```

上面这十几行，就是那个订单 demo 的核心——一个链、一个本地模型、一条 prompt。没有框架也能写，框架只是把胶水粘得更顺手。

## 反转：其实早就写过一套「迷你 agent 框架」

回到我那辅食 App。它没引任何编排框架，却自己实现了一整套：

- `LLMToolDefinition` 把工具的参数 schema 写死，发出去约束模型吐什么形状；
- `LLMToolCallAccumulator` 按 `index` 把流式 tool_calls 拼回去，非法 index 直接丢；
- `BabyFoodTool.parseArguments:` 把模型吐回来的字段逐个强校验、清洗、兜底（枚举命中失败 → 安全默认、超长截断、字符串强转数字）；
- 校验失败返回 error，调用方走「重试 / 规则兜底 / UI 提示」闭环。

这套东西，正是 LangGraph / CrewAI 在中间层做的事——**Tool Calling 的契约与校验**。只是没用框架，而是用 ObjC 手写了一遍。

这反而是好事。2026 年的共识很明确：**单 agent、调几个工具时，手写 loop 比引框架更轻、更可控、更易调试。** 我那辅食 App 就是证据：它没有多智能体、没有复杂状态机，一个 `LLMDirectClient` + 一组 Tool 解析就够。引入 LangGraph 反而是过度设计。

所以别再问「该用哪个框架」——最合适的方案已经在手上了（手写 loop + llama.cpp），只是没把它叫成「框架」。

## MCP：为什么 2026 年它是标配

那套 Tool schema，现在只能被我那辅食 App 自己用。但有一个协议叫 **MCP（Model Context Protocol）**，专门把「工具 / 数据源」标准化——`BabyFoodTool` 只要包一层 MCP server，Claude 桌面端、LangChain、任何支持 MCP 的客户端都能直接调用，不用为每个框架重写一遍。

这正是博客系列（三）讲的「契约」思想的外扩：schema 定义一次，到处复用。手上的 `BabyFoodTool` 已经是 MCP server 的雏形，只差一层协议封装。

## 选型决策：用提问带推理，别背清单

下次有人问「端侧 Agent 用什么框架」，别甩表，带他走一遍：

1. **模型在哪跑？**
   - 端侧、要兼容各种模型 → llama.cpp（软解思路）；
   - 端侧、追求省电且模型已转好 → Core ML（硬解思路）；
   - 端侧、场景简单、iOS 26+ → Foundation Models（系统播放器）；
   - 云端 → 这层不用管，跳过。
2. **编排有多复杂？**
   - 单 agent、调几个工具 → **手写 loop 就够了**（我那辅食 App 的范本），别急于引框架；
   - 多步、要状态 / 回滚 / human-in-the-loop → LangGraph；
   - 多角色协作 → CrewAI；
   - 只想快速跑通 prototype → LangChain。
3. **工具要不要被多方复用？**
   - 是 → 把 Tool 做成 MCP server，未来任何框架都能接。

走完这三问，答案自己就出来了，比记二十个框架名字有用。

## 小结

业内有句话：**模型 > prompt > 框架选择**。框架是最不值钱的那一层——它不决定 agent 聪不聪明，只决定写胶水代码累不累。

现在的牌面已经不错：底层有 llama.cpp 辅食 App 实战，中间层有 LangChain 订单 demo 练手，还顺手在 ObjC 里手写了套 Tool 约束。先把这两张牌打熟，等真遇到「多智能体 / 长任务状态」的刚需，再上 LangGraph 或 Foundation Models——**别为用框架而用框架**。

> 系列（一）认识了端侧 Agent 的链路，并论证了一件事：**Agent 的大量工程能力，可以复用传统互联网的那些老本事**。
> 系列（二）把视角收进「体验」：首字耗时、流式、离线、功耗，本质和播放质量治理是同构的。
> 这篇聊一个更靠前的决定：**端云到底怎么分工**。它决定了前面所有的体验优化往哪使劲。

## 先从一个会翻车的场景说起

地铁里，信号一格。用户对 App 说："帮我记一下，明天早上九点提醒我买菜。"

在「纯云端」架构下，这句话的旅程是这样的：

```text
用户说话 → App 发到云端 → 云端做意图识别
        → 云端决定调哪个 tool → 云端返回指令 → 端侧才去建提醒
```

结果呢？转圈圈，超时，失败。用户骂了一句："我手机就不能自己记一下吗？"

这句话其实戳中了端云结合最核心的错位——**端侧明明有算力、有本地数据、还能离线，却被当成了"显示器 + 键盘"：只负责输入和展示，所有脑子都在云端**。

前面学的那些「弱网降级、离线可跑、本地模型」，在这个架构里全成了摆设。所以这篇不急着写代码，先把「端和云该怎么摆」想透。

## 一、先承认：纯云端架构本身没错，只是放错了地方

这个判断是对的——这种架构，是标准 SaaS 对话产品的做法（各类聊天 API 都长这样）：

- 启动上报 `uid` 和「当前可用的 tools」；
- 之后只要拿 `chatId` 发 `messageId` 就行，指令很轻；
- 服务端统一拼 Prompt、做 A/B、调优、切 Agent，非常灵活；
- 弱网下靠 `chatId` 续传，抗击能力强。

**在「纯云端 Agent」这个前提里，它完全成立，甚至是最优解。** 服务端掌控一切，好迭代、好观测、好实验。

问题出在：目标是**端云结合**，而这套架构的隐含假设是「端侧没有脑子」。一旦端侧也有 LLM、也有本地 tool，这个假设就破了，于是出现五个错位：

1. **简单意图也被网络绑架**。开灯、记备忘、查本地文件——这些本地就能做的，也得先发云端判断再回来执行。弱网下延迟高，离线直接哑火。系列（二）反复强调的「弱网降级 / 离线可跑」，在这个架构里根本没入口。
2. **和「减少端侧传输」自相矛盾**。靠 `chatId`/`messageId` 省了指令，但为了云端拼 Prompt、决策 tool，端侧反而得把**对话历史、系统状态、本地 tool 结果**持续上送。省了指令，亏了上下文。
3. **本地 tool 结果被迫上云**。相册、定位、文件这类隐私数据，本可在端执行，现在要先传云端才能被用——隐私和流量双输。
4. **启动上报 tools 会过期**。tools 是动态的：装了新技能、权限变了、上下文变了，只在启动报一次立刻失效；而且端侧几十个 tool 的 schema 本身就不小。
5. **离线零可用 + 体验不可控**。A/B、Prompt 调优全在服务端，端侧无法保证离线一致性，也无法做本地个性化。

把这五个错位翻译成前面那句播放器类比：**纯云端架构，等于"每看一片都得联网从云端拉，断网就黑屏，而且云端全知道看了什么"**。而端云结合，应该是「热门/私人的片缓存在本地播放器，冷门/超清/新片才从云拉」。

所以结论先立住：**端云结合的底座，不是"云端为主、端侧做壳"，而是"端侧有脑子、云端是外挂"**。带着这个立场，来看两个最纠结的问题。

## 二、第一个问题：Prompt 到底在哪拼？

先讲痛点。模型在端，Prompt 自然该在端拼；模型在云，Prompt 自然该在云拼——这句话听起来理所当然，但一碰到诉求就拧巴了：

- 想让服务端做 A/B、热更新 Prompt、挂 RAG 结果——这些**必须发生在云端**，端侧不能写死；
- 可如果每次都让端侧把全部对话历史和本地状态上传，又回到了第一节的矛盾 2：省了指令，亏了上下文。

那怎么办？答案是**尽量靠近"真正执行模型的那个端"**，但为了保留想要的灵活性，用一种混合编排：

```text
云端负责：下「模板 / 策略」
         —— 可热更新、可做 A/B 变体、可挂 RAG 结果、可下发 few-shot 示例

端侧负责：做「填充 / 组装」
         —— 把云端模板 + 本地个性化片段
            （长期偏好、当前页面、电量、位置等实时状态）
            + 本地 tool schema
         拼成最终 Prompt，再喂给「端或云」的模型
```

记住：**模板在云，填充在端**。

这样做的好处是双面的——服务端照样能快速迭代 Prompt、做 A/B（想要的灵活一点没丢）；同时端侧**不必上传全部上下文**，只在「切云端」时发「已组装好的 Prompt 或增量」，云端不再从头拼（矛盾 2 化解了）。

继续用播放器的类比：这就像**字幕和播放列表**。通用的翻译风格、推荐算法（模板）从云端下；而"我的播放列表、我的字幕偏好"（个性化）永远在本地拼。云端不知道具体在放哪一帧，但它给的推荐策略是新鲜的。

落到工程上，端侧跑本地 LLM 时，Prompt 全在端拼，云端只管下发模板；切云端时，端侧把"拼好的 Prompt"发过去，云端别再重复拼一遍。

## 三、第二个问题：模型怎么"切分"，意图识别怎么做？

先澄清一个最容易被带偏的点：**这里的"切分"不是把一个模型切开**。把一个模型纵向切开那是 MOE / 模型并行，端侧根本不现实。要切的是**任务 / 能力**——哪些意图端侧 LLM 扛，哪些甩云端。

那"该谁扛"这个判断本身，怎么做？这就是意图识别。这里有个**铁律**：

> 意图识别本身必须足够轻。如果为了"判断意图"先发一次云端，那端侧兜底的意义就归零了——断网时连"该不该上云"都判断不了。

所以意图识别要在**端侧、要快、要省**。具体三招，从粗到细：

1. **规则先行**。命令式、"打开 XX""记一下 XX"这种带固定槽位的、或者离线触发词，直接端侧正则/匹配拦截，**根本不过模型**。能不过模型就别过。
2. **端侧轻量路由**。过不了规则的，交给一个极小的 0.5B / 1B 模型（正好是系列里"分层模型"的自然延伸），或者一个 ML 分类器，判断这句话是"本地可执行的简单意图"还是"需云端的复杂意图"。
3. **置信度阈值 + 网络探测**。小模型不光给类别，还给一个置信度；**低置信度才上云**。同时主动测 RTT / 是否离线，离线或高延迟时强制走端侧。

翻译成播放器类比就是：**播放器先判断"这片本地有缓存吗、画质本地够吗"**——有就本地放，没有且网络好就联网拉，网络差就放本地低清版并提示。意图识别，就是这个"先判断"的瞬间。

## 四、把上面三节串成一个闭环：弱网降级

前面说的路由、Prompt 编排，最终要落成一个能抗网络的闭环。它长这样：

```text
用户一句话
   │
   ├─ 规则命中本地意图？── 是 ──→ 端侧 LLM 直接执行 + 本地 tool（任意网络都行）
   │
   └─ 需模型判断？
         │
         ├─ 网络好 ──→ 发云端（端侧已拼好 Prompt 增量）
         │
         └─ 网络差 / 离线 ──→ 端侧小模型兜底
                                 （尽力答 + 明确提示"网络不佳，用了本地模型"）
                                 请求入队，网络恢复后可选补发云端
```

注意这里面**端侧永远有退路**：简单意图不依赖网络；复杂意图在弱网下也有"本地尽力版"，而不是白屏或转圈到天荒地老。这正是系列（二）讲的弱网降级，从"认知"落成了"架构动作"。

## 五、数据同步：本地写，上线 reconcile

前面几节把"算力怎么分、Prompt 在哪拼"讲透了，但端侧一持有数据，就绕不开一个老命题：**两份数据怎么对齐**。它不是一个新题，传统互联网的"离线优先（offline-first）"早就趟过坑，端云结合只是把它重新摆到面前。

先讲痛点（一个会翻车的场景）。用户在地铁里离线建了个提醒，到家打开平板，提醒没同步——丢了。或者更糟：离线记了条笔记，联网后被重复写入两遍（弱网重试没去重）。再或者，云端想用他的长期偏好做个性化，结果发现偏好全锁在手机里，换设备就归零。这几件事背后是同一句话：**端侧持有数据之后，"本地"和"云端"这两份必须能对上**。

用前面那句播放器类比接着说：这就像**跨设备续播进度**。在手机看到第 20 分钟，换平板要能从 20 分接着放——这个进度存在哪、怎么同步、两台设备同时看谁覆盖谁，就是端云数据同步的翻版。

先立一个总原则，回答"主副本在哪"：

> **端侧持有主副本（前面定的），云端是镜像 + 跨设备汇聚点，不是唯一真相源。**

为什么不能反过来（云端主、端侧缓存）？因为那样离线就写不了、弱网又回到"事事问云端"的老路，把端侧的优势全废了。端侧主，才能离线照写、联网再补。

那"上线 reconcile"具体怎么做？几件事，从粗到细：

1. **离线优先，乐观写入**。端侧先落本地（建提醒、记笔记、改偏好），立刻返回成功，不等云端。这和"弱网降级"一脉相承——能本地做的，先本地做完。
2. **增量同步，别全量**。只传"变了的那条"，不每次把整个上下文重新上送。这正好呼应最初"减少端侧传输"的诉求：变化的 delta 才上云，全量留在端。
3. **幂等 + 去重，扛重试**。弱网重发会导致重复。每条本地写入带一个本地生成的稳定 ID（UUID），云端按 ID 去重——收到同 ID 就覆盖不是新增。这是 offline-first 的标配，不然后面全是脏数据。
4. **冲突解决要有规则**。两台设备同时改了同一条怎么办？常用三招：**最后写入获胜（LWW，带时间戳）** 最简单；**版本向量**更严谨但重；**分字段合并**适合"提醒时间改了、内容没改"这种局部冲突。端侧场景大多用 LWW 就够了，别过度设计。
5. **隐私分级，决定"能不能上云"**。不是所有端侧数据都该同步：提醒、笔记这类可上云做跨设备/备份；相册、定位、屏幕内容这类高敏数据，**只留端、永不主动上云**（最多用户显式触发才传）。同步策略本身就得带一个"隐私开关"。

把这几条收成一句：**端侧主写、增量上云、ID 幂等、LWW 兜底、敏感隔离**。

注意一个和前面"模板在云、填充在端"的呼应：同步上去的，是**用户的长期数据（偏好、历史、产物）**，不是每轮对话的临时上下文。临时上下文留在端做实时拼装，只有"值得跨设备保留"的才进同步通道。两者分工清楚了，传输量和隐私都压得住。

## 六、端云结合的几条硬规矩

写到这，端云结合的样子就清楚了。压成几条不可妥协的规矩：

- **端侧要有本地 Agent / 路由层**（博客里那个 LLM Loop），不是哑终端。它负责意图识别、本地执行、弱网兜底。
- **能本地执行的 tool 绝不上云**，只把结果摘要回传。隐私数据不出端，流量也省。
- **端侧持有上下文主副本**，云端按需拿增量，而不是云端永远是唯一真相源。
- **Prompt 模板在云、填充在端**，服务端照常做 A/B 和调优，但不逼端侧裸奔上传全量上下文。

回到最开始那句类比收个尾：**纯云端是"断网黑屏的在线播放器"；端云结合是"带本地缓存、能离线放、热门自动缓、冷门联网拉"的播放器**。端侧那点算力和本地数据，是最贵、也最该用好的资产，别把它只当块屏幕。

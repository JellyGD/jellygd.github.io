> 这个系列想把「移动端 AI Agent」当作一个**工程问题**来学习，而不是只聊模型。计划分三篇：
>
> 1. 本篇：先认识端侧 Agent 是什么、它的完整链路长什么样，以及——**优化方向上哪些传统互联网能力可以直接复用**。
> 2. 端侧体验优化：首字耗时、流式、本地模型、UI 生命周期、离线降级。
> 3. 生成可控性：Agent 生成是不可控的，如何让输出符合预期。
>
> 如果你做过客户端或服务端研发，会发现这一篇里大量内容“似曾相识”——这正是重点。

## 为什么要单独聊「移动端」AI Agent

AI Agent 在 Web 和服务端已经有很多实践，但直接搬上手机，约束完全不同：

- **设备异构**：从旗舰机到百元机，NPU 算力、内存、系统版本差异极大，同样的能力在低端机上可能完全跑不动。
- **电量与发热**：本地推理是耗电大户，长时间 Agent 会话会烫手、掉电、被系统降频。
- **网络不确定**：地铁、电梯、弱网是常态，云端 LLM 的每次调用都可能超时。
- **隐私红线**：相册、日历、短信、屏幕内容都是高敏数据，不能无脑上传。
- **UI 生命周期复杂**：App 切后台、横竖屏、列表复用、页面销毁——这些移动端经典坑，Agent 的 UI 同样要踩。

所以端侧 Agent 不是“把 ChatGPT 塞进 App”，而是一套**在强约束下把感知-决策-执行-反馈跑通**的工程系统。

## 一、先澄清几个核心概念

很多文章一上来就讲架构，但概念没对齐，后面全是黑话。先用大白话对齐。

### 1. AI Agent 是什么

一句话：**Agent = 能自己决定“下一步做什么”并调用工具去做的程序**，而不是“你问一句它答一句”的问答机器人（ChatBot）。

它和纯 LLM 对话的本质区别是闭环：

```text
普通对话：输入 → 模型 → 输出（结束）
Agent：    输入 → 模型(决定调哪个工具) → 执行工具 → 拿到结果 → 模型(再决定) → ... → 输出
```

Agent 会根据用户输入做意图识别，把任务拆解成若干执行步骤，再经过「决策」和「执行」两个环节，**多步循环**地推进，直到任务完成或到达停止条件。

### 2. Tool / Function Calling：Agent 的“手”

LLM 本身只会“说话”，不会“做事”。要让它发消息、查订单、改设置，就得给它工具。

工具本质上是一个**带 schema 描述的函数**：名字、用途、参数结构。模型根据自然语言，输出“我要调这个函数、参数是这些”，运行时再去真正执行。

```text
tool: send_message(to, content)
model output: { "tool": "send_message", "args": { "to": "张三", "content": "会议改到三点" } }
runtime: 真正调用 IM SDK 把消息发出去
```

这里有两个常被混用的词：**Function Calling** 和 **Tool Use**。在业界，它们本质上描述的是同一种能力——都是“模型决定调用某个工具并产出参数”（OpenAI 称之为 Function Calling，Anthropic 称之为 Tool Use）。

但为了把 Agent 的执行链路讲清楚，更值得区分的是**「模型决策」和「运行时执行」这两步**：

- **模型决策（对应你说的 Function Calling）**：LLM “大脑”给出指令——要调用哪个工具、参数是什么。这一步只产出一段结构化的“调用意图”，并没有真正发生任何动作。
- **运行时执行（对应你说的 Tool Use）**：你的代码拿到这个意图，真正去调用系统能力或 SDK，**实际操作用户的手机**（发消息、改设置、查数据库）。

记住这个拆分很有用：Agent 出 bug，第一步就要判断——是“模型决策错了”（调错了工具 / 参数不对），还是“运行时执行错了”（工具实现有 bug / 权限被拒）。

### 3. 端侧 vs 云端：三种部署形态

| 形态 | 说明 | 典型场景 |
| --- | --- | --- |
| 纯云端 | 所有推理走服务端大模型 | 复杂任务、需要最强能力 |
| 纯端侧 | 小模型跑在 NPU 上（如 Apple Intelligence、端侧 3B 模型） | 离线、隐私、低延迟简单任务 |
| 混合 | 端侧做意图初筛/简单动作，复杂推理上云 | 大多数生产级 App |

端侧的价值是**隐私、零延迟、离线可用**；云端的价值是**能力上限高**。工程上几乎都是混合，难点是“什么时候该上云、什么时候端侧能扛”。

#### 怎么选：纯端侧 / 纯云端 / 混合

- **优先纯端侧**：离线或弱网场景、数据不出端的高隐私场景、延迟敏感且逻辑简单的任务（本地快捷指令、简单分类）。注意：端侧对硬件有要求，低端机反而“扛不动”，不能硬上。
- **走纯云端**：需要复杂推理、长上下文、最强能力的任务；开放域问答；需要实时联网信息；或端侧算力/内存明显不足时。
- **混合（最常见）**：端侧做意图初筛、隐私数据处理、简单动作；复杂任务上云做拆解与执行；云端结果回端渲染或落地执行；网络不佳时由端侧兜底。

#### 这里的关键机制：意图识别

“什么时候上云、什么时候端侧”本身，靠的就是**意图识别**：把用户的一句话或一个动作，映射成“要做什么、要不要调工具、调哪个、上云还是端侧”。

常见做法有几种，通常分级组合：

- **规则 / 关键词**：快、可控，适合固定场景（如“打开 XX”“发消息给 XX”），但覆盖不了开放表达。
- **端侧小模型分类**：轻量、隐私、低延迟，适合做粗筛（这条直线任务端侧能搞定吗？）。
- **云端大模型理解**：复杂、开放域，适合需要深度语义解析的任务。
- **分级策略**：端侧先粗分，简单的本地解决；拿不准或复杂的，带上上下文上云细解析。再配合**置信度阈值**——低于阈值就兜底或追问，避免误判。

> 意图识别怎么做更细，我们会在（二）端侧体验优化里展开。

### 4. Context / 上下文：Agent 的“工作记忆”

Agent 每做一次决策，依赖的上下文包括：

- 对话历史
- 设备状态（当前页面、App 在前台还是后台、网络类型）
- 环境信息（屏幕语义、地理位置、相册/日历摘要）
- 已调用工具的返回结果
- 系统提示词（system prompt）

上下文是有限的（token 上限），所以**“塞什么、丢什么”是端侧 Agent 的核心工程问题**。

#### 上下文 token 有限，怎么优化

工程上常见的裁剪策略：

1. **保留最近 N 轮对话**（注意是“最近”而非“最开始”），保证当前任务连贯；过早的轮次再处理。
2. **对更早的轮次做压缩摘要**，保留关键决策与结论，丢掉原始长文本。
3. **二次压缩**：当压缩后的上下文仍逼近上限，再做一轮裁剪（如摘要套摘要、只保留工具结果与待办），腾出空间给新信息。

#### 摘要怎么生成

- **模型摘要**：把旧对话交给 LLM，要求输出结构化摘要（保留了哪些决策、工具结果、未决问题）。质量高，但有额外耗时与成本。
- **抽取式摘要**：不调模型，直接保留关键结构化信息（已完成的工具调用、用户偏好、待办事项），丢弃纯闲聊。成本低、可控性强。

工程上常两者结合：**结构化信息直接保留，长文本交给模型压缩**。

### 5. RAG / 检索增强：把知识塞进上下文

很多业务知识不在模型权重里（内部文档、用户数据、实时信息）。RAG 的做法是：先检索相关内容，再拼进上下文，让模型“现学现用”。

```text
用户问 → 检索知识库(向量/关键词) → 取 TopK 片段 → 拼进 prompt → 模型回答
```

### 6. Agent Loop：一次交互的完整循环

把上面串起来，一个最小 Agent 循环是：

```text
loop:
  1. 收集上下文（对话 + 设备 + 工具结果）
  2. 模型决策（直接回答 / 调工具 / 停止）
  3. 若调工具：执行 → 把结果写回上下文
  4. 若直接回答或到达停止条件：退出循环
```

理解了这个循环，后面所有“体验优化”和“可控性”问题，都是在优化这个循环的**某一步**。

## 二、端侧 AI Agent 的完整链路

把概念落到移动端，一次 Agent 任务从触发到结果，通常经过这些环节：

```text
用户触发
  │  （语音/文字/点击入口/系统事件/快捷指令）
  ▼
端侧上下文采集
  │  （屏幕语义 · App 状态 · 位置 · 相册/日历摘要 · 网络类型）
  ▼
意图理解 / Planning
  │  （端侧小模型初筛 → 复杂任务上云大模型拆解子步骤）
  ▼
Tool 调度与执行
  │  （调 API · 操作 UI · 发消息 · 查数据库 · 系统能力）
  ▼
执行结果回写与校验
  │  （拿到工具返回值，判断是否成功/需要重试）
  ▼
UI 渲染 / 系统回执
  │  （流式输出 · 卡片 · 通知 · 后台任务）
  ▼
反馈与修正
     （用户纠正 · 自动重试 · 评测打分 · 进入下一轮 Agent Loop）
```

每个环节都可能出问题：上下文采错 → 意图理解偏 → 调错工具 → 执行超时 → UI 没渲染出来。这跟我们之前聊的**视频播放链路**（业务下发→网络→解码→渲染）本质上是一类问题：**长链路、多环节、任一环节异常都会体现在最终体验上**。

## 三、重点：优化方向上，哪些传统互联网能力可以复用

这是本篇最想传达的一点。Agent 是新技术，但**支撑它的工程能力，大量是传统互联网早就验证过的**。不要从头造轮子。

下面按“能力 → 在 Agent 里怎么用”一一对应。

### 1. 可观测性 / 埋点 → Agent Tracing

传统研发靠埋点看崩溃、卡顿、转化。Agent 同样需要，但粒度要细到**每一步**：

- 每次模型调用的 token 数、耗时、是否命中缓存
- 每次 Tool 调用的名称、参数、返回、是否成功
- 每轮 Agent Loop 的步数、总耗时
- 最终是否完成任务、用户是否纠正

把这些串成一条 **`agentSessionId`** 的 trace，排查“为什么它调错了工具”“为什么这么慢”才有据可依。这跟播放质量治理里用 `playSessionId` 串联整条链路是同一个思路。

### 2. 灰度发布 / Feature Flag → 新 Agent 能力按维度放量

新 Agent 能力（新 prompt、新工具、新模型）不要全量上。按**机型、系统版本、App 版本、用户分层**灰度：

- 低端机先不开本地模型
- 新 prompt 先在 5% 用户验证效果
- 出问题一键关开关，不发版

这是客户端研发做了十年的基本功，Agent 时代直接复用。

### 3. A/B 实验 → 对比不同策略

Agent 有大量“策略选择”问题，天然适合 A/B：

- 不同 system prompt 哪个任务完成率高
- 云端模型 vs 端侧模型 vs 混合，体验/成本怎么权衡
- 不同兜底策略（重试几次、何时转人工）哪个用户满意度高

把“调 prompt”从玄学变成可度量的实验。

### 4. 缓存/CDN → 相似请求与知识预取

- **Prompt 缓存**：相同/相似上下文的开头部分（system prompt、长知识）可缓存，省 token、降延迟。
- **知识库预取**：根据场景提前把可能用到的知识拉到端侧/CDN 边缘，RAG 时本地命中。
- **结果缓存**：确定性查询（如“查我的订单状态”）可短期缓存，避免重复调模型。

### 5. 重试 / 降级 / 熔断 → LLM 与 Tool 的容错

大模型调用和工具调用都不可靠，传统容错三件套直接上：

- **重试**：模型超时、Tool 偶发失败 → 有限次重试
- **降级**：云端超时 → 切本地小模型；本地模型答不出 → 走规则兜底；Tool 失败 → 给候选方案
- **熔断**：某模型/某工具错误率过高 → 暂时停用，避免雪崩

注意：**每次降级都要上报原因和结果**，否则线上问题被“悄悄兜住”，你永远不知道它发生过（这点我们在播放自愈里也强调过）。

### 6. 性能 Profiling → 首字耗时与端到端耗时

用户感知的核心是延迟。要像做首帧优化一样盯：

- **TTFT（Time To First Token）**：从发请求到第一个字出来的时间
- **端到端耗时**：从用户触发到任务完成
- **电量/内存**：本地推理对续航的影响
- **流式渲染**：边生成边显示，别等全部生成完才出

这些指标的定义方式、采集方式，和起播耗时、首帧耗时几乎一模一样。

### 7. 状态机 → Agent 会话生命周期

Agent 会话有明确的阶段流转，适合用状态机管理，避免“重复触发”“状态错乱”：

```text
idle → understanding → planning → acting(tool) → observing → ... → done / failed
```

而且要**单向流转 + 关键操作串行化**，和播放器状态机（`preparing → playing → paused`）是同一套方法论。列表里多个 Agent 卡片并发时，也要像播放器复用那样管理好会话实例。

### 8. 错误分类与归因 → 跟播放质量治理同源

把 Agent 失败按维度聚合：

- Top 机型（端侧模型兼容问题）
- Top 工具（某个 Tool 失败率高）
- Top 模型/Provider（云端某模型超时）
- Top 意图类型（某类任务完成率低）

这套归因看板，和我们做黑屏/花屏按机型、CDN、编码维度拆，思路完全一致。**会做播放质量治理，就会做 Agent 质量治理。**

### 9. UI 生命周期 → 移动端老本行

Agent 的 UI 跑在 Activity/ViewController 上，移动端那些经典坑一个都跑不掉：

- 页面销毁后 Agent 还在回调 → 野指针/崩溃
- 列表复用导致会话卡片绑定错乱
- 切后台后流式中断、回来要恢复
- 渲染 View 尺寸为 0 → 内容不显示

这些不是 AI 问题，是**移动端基本功**，恰恰是客户端工程师的相对优势。

### 10. 端上数据回流 → 让问题可复现

和播放问题一样，Agent 问题高度依赖现场（某个机型、某次网络、某段对话）。必须让一次会话**可回放、可串联、可归因**——靠的就是前面说的 `agentSessionId` + 完整 trace 回流。

---

小结一下：**Agent 的“智能”来自模型，但 Agent 的“能用”来自工程**。而这套工程能力，70% 是传统互联网已经打磨成熟的，剩下 30% 才是 Agent 特有的（prompt、tool schema、上下文管理、生成可控性）。这也是为什么客户端/服务端工程师转型做 Agent，比纯算法出身更有落地优势。

## 四、系列路线图

- **（二）端侧体验优化**：TTFT 与流式、本地模型选型、上下文裁剪、意图识别与分级路由、UI 生命周期适配、弱网/离线降级、电量控制。
- **（三）生成可控性**：Agent 生成不可控怎么办——prompt 工程、结构化输出与 schema 校验、约束解码、评测闭环、human-in-the-loop、失败重试与兜底。

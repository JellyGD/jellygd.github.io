# 视频播放花屏绿屏黑屏排查与治理

## 摘要

视频播放中出现花屏、绿屏、黑屏，本质上是播放链路中某个环节出现了异常。这个链路通常包括：业务下发、鉴权、调度、DNS、建连、CDN、拉流、Demux、解码、同步、渲染、View 生命周期以及业务状态机。

因此，这类问题不能只靠“看日志”或者“切软解”来处理，而应该建立一套完整的播放质量治理闭环：

1. 监控发现：通过端上埋点、播放器事件、帧级检测、服务端日志发现异常。
2. 数据回流：将一次播放会话中的资源、网络、解码、渲染、状态机、设备环境完整串起来。
3. 分层排查：按资源层、网络层、容器层、解码层、渲染层、业务层逐步收敛原因。
4. 修复兜底：针对不同根因做转码修复、CDN 切换、软硬解降级、重建渲染链路、播放器状态恢复等。
5. 预警防复发：按机型、版本、资源、CDN、编码格式、播放器内核等维度做阈值预警和趋势预警。

面试中可以把这个问题回答成“播放质量可观测性 + 端上自愈 + 服务端治理 + 预警体系”的闭环，而不是单点排障。

## 一、先识别异常类型

### 1. 花屏

花屏通常指画面出现马赛克、色块、撕裂、局部异常纹理、帧内容错乱等现象。

常见原因：

- 源文件损坏，转码输出异常。
- HLS/DASH 分片损坏或缺失。
- CDN 缓存了错误内容。
- 网络中断导致分片不完整。
- Demux 后 packet 数据异常。
- 解码器容错失败。
- 硬解兼容性问题。
- 解码输出的 YUV buffer 内容异常。
- stride、slice height、alignment 处理错误。
- 渲染纹理复用错误。
- 多线程读写 video frame buffer 出现时序问题。

典型判断方式：

- 同一视频所有设备都花屏：优先怀疑源文件、转码、CDN。
- 同一视频只有部分机型花屏：优先怀疑硬解兼容性。
- 只在 seek、切清晰度、横竖屏后花屏：优先怀疑播放器状态机或渲染链路。
- 只在播放一段时间后花屏：可能是 buffer 生命周期、纹理复用、解码器状态污染。

### 2. 绿屏

绿屏通常表现为整个画面变绿，或者大面积绿色块。它往往和 YUV 数据解释、硬解输出、颜色空间转换、渲染链路有关。

常见原因：

- YUV 转 RGB 失败。
- NV12、NV21、I420 等像素格式识别错误。
- U/V 分量顺序错误。
- 解码器输出 buffer 异常。
- 硬解输出的 color format 和渲染层预期不一致。
- Metal/OpenGL shader 采样错误。
- Texture 绑定错误或复用错误。
- Surface 生命周期异常。
- 某些机型对 H.265、HDR、10bit、特殊 profile 支持不完整。

典型判断方式：

- 切软解后正常：高概率是硬解兼容性问题。
- 截取 YUV 数据本身正常，但渲染后绿屏：高概率是渲染或颜色转换问题。
- 只有特定编码格式绿屏：看编码 profile、level、bit depth、color range、color space。
- 前后台切换后绿屏：看 Surface/Texture 是否被销毁后未重建。

### 3. 黑屏

黑屏是最复杂的一类，因为它既可能是播放链路真的没有视频输出，也可能只是 UI 或渲染层没有显示出来。

常见原因：

- 播放未真正起播。
- 首帧未解码出来。
- 解码有输出，但没有送到渲染层。
- 渲染层绑定失败。
- View 尺寸为 0 或被遮挡。
- 播放器进入 playing，但 video clock 没有推进。
- 有音频无视频，或音频时间戳推进但视频帧没有渲染。
- DRM、鉴权、业务风控导致视频数据不可用。
- 进入后台再回来后 Surface 丢失。
- Feed/列表复用中播放器实例与渲染 View 绑定错乱。
- seek 或切清晰度后状态机没有恢复。

典型判断方式：

- 有声音但无画面：优先看解码输出和渲染链路。
- 无声音也无画面：优先看起播、网络、鉴权、状态机。
- 只有首帧黑屏：看首帧超时、首帧回调、首帧渲染。
- 后台回来黑屏：看 Surface/Texture 生命周期。
- 列表滑动后黑屏：看播放器复用和 View 绑定。

## 二、监控发现

### 1. 播放质量核心指标

线上监控需要覆盖完整播放生命周期。

基础播放指标：

- 播放请求量。
- 播放成功率。
- 起播成功率。
- 播放失败率。
- 播放错误码分布。
- 起播耗时。
- 首帧耗时。
- 首帧失败率。
- 播放完成率。
- 播放中断率。

体验指标：

- 卡顿率。
- 卡顿次数。
- 卡顿总时长。
- 平均卡顿时长。
- 卡顿恢复成功率。
- 清晰度切换成功率。
- seek 成功率。
- seek 后首帧耗时。

画面异常指标：

- 黑屏率。
- 疑似黑屏率。
- 有音无画率。
- 绿屏率。
- 疑似绿屏率。
- 花屏率。
- 首帧渲染失败率。
- 视频帧渲染中断次数。
- 视频帧长时间无更新次数。

解码渲染指标：

- 解码器创建成功率。
- 解码失败率。
- 硬解失败率。
- 软解降级率。
- 解码输出帧率。
- 渲染输出帧率。
- 解码队列积压。
- 渲染队列积压。
- 丢帧数。
- 音视频同步偏移。

### 2. 黑屏检测策略

黑屏不能只依赖用户反馈，可以通过状态组合自动判断。

典型检测条件：

- 播放器状态为 playing。
- 音频 clock 持续推进。
- 视频帧超过 N 秒没有渲染。
- 当前渲染 View 可见，且尺寸大于 0。
- 没有主动 pause、后台、页面不可见等业务状态。

如果满足这些条件，可以上报“疑似黑屏”。

伪逻辑：

```text
if playerState == playing
   and audioClockProgressing == true
   and lastVideoRenderTime > 3s
   and renderViewVisible == true
   and appInForeground == true:
       report suspected_black_screen
```

也可以增加画面像素采样：

- 低频采样当前渲染帧。
- 判断亮度是否长期接近 0。
- 排除本身就是黑场的视频片段。
- 结合音频推进和视频帧时间戳判断，降低误报。

注意：电影转场、片头黑场、暗色视频内容可能导致误判，所以黑屏检测最好结合播放状态，而不是只看画面颜色。

### 3. 绿屏检测策略

绿屏可以通过低频像素采样判断。

检测思路：

- 每隔几秒抽样一帧。
- 对画面做缩小采样，例如采样 16x16 或 32x32 网格。
- 计算绿色通道占比。
- 如果大面积像素满足 G 明显高于 R/B，并持续多次出现，则上报疑似绿屏。

需要注意：

- 足球场、草地、游戏场景可能天然绿色多，需要结合持续时间和画面变化判断。
- 不建议每帧检测，避免影响性能。
- 检测结果应作为疑似异常，而不是绝对异常。

### 4. 花屏检测策略

花屏自动检测比黑屏、绿屏更难，可以采用轻量启发式：

- 画面局部块状颜色突变。
- 相邻帧像素差异异常巨大。
- 局部区域长时间出现高频噪声。
- 解码器有错误日志或丢帧异常。
- 渲染帧 checksum 异常。

更可行的方式是结合：

- 解码错误码。
- 播放器内部错误事件。
- 用户投诉入口。
- 自动截图抽样。
- 资源验片结果。

### 5. 维度聚合

所有异常指标都不能只看全局平均值，要按维度拆开看。

关键维度：

- App 版本。
- 播放器 SDK 版本。
- 机型。
- 芯片。
- 系统版本。
- 网络类型：Wi-Fi、4G、5G。
- 运营商。
- 地域。
- CDN 厂商和节点。
- videoId。
- 清晰度。
- 编码格式。
- 封装格式。
- 是否硬解。
- 是否 HDR。
- 是否 DRM。
- 是否直播、点播、短视频、长视频。

很多问题只有在细分维度下才明显。例如全局黑屏率只有 0.1%，但某个机型上的 H.265 绿屏率可能达到 20%。

## 三、排查数据回流

### 1. 为什么需要完整数据回流

播放问题往往具有强现场性。用户出现问题时，研发本地不一定能复现，因为它可能依赖：

- 某个视频资源。
- 某个 CDN 节点。
- 某个机型。
- 某个系统版本。
- 某次 Range 请求返回。
- 某个播放器状态切换时机。
- 某个前后台生命周期。

所以必须让一次播放会话可回放、可串联、可归因。

### 2. 播放会话 ID

建议每次播放生成 `playSessionId`。

它应该贯穿：

- 业务播放请求。
- 播放器初始化。
- 网络请求。
- CDN 访问日志。
- 解码器创建。
- 渲染事件。
- 错误上报。
- 用户操作。
- Crash 日志。

有了 `playSessionId`，排查时就能还原完整链路，而不是在多套日志之间手工猜测。

### 3. 资源信息

需要回流：

- videoId。
- assetId。
- 播放 URL。
- 清晰度档位。
- 码率。
- 分辨率。
- fps。
- 时长。
- 封装格式，例如 MP4、HLS、DASH、FLV。
- 编码格式，例如 H.264、H.265、AV1、VP9。
- profile。
- level。
- bit depth，例如 8bit、10bit。
- color space，例如 BT.709、BT.2020。
- color range，例如 full range、limited range。
- 是否 HDR。
- 是否 DRM。
- 音频编码格式。
- 音视频轨数量。

### 4. 网络信息

需要回流：

- DNS 耗时。
- TCP 建连耗时。
- TLS 耗时。
- 首包耗时。
- 下载速度。
- HTTP 状态码。
- CDN 节点。
- CDN IP。
- Host。
- Range 请求区间。
- 分片 URL。
- 分片下载成功率。
- 分片大小。
- 分片校验结果。
- 重试次数。
- 是否切 CDN。
- 是否命中缓存。

### 5. 播放器状态信息

需要回流状态流转，例如：

```text
idle -> preparing -> prepared -> buffering -> first_frame_rendered -> playing -> paused -> completed
```

异常时要知道卡在哪个状态：

- 是否进入 prepared。
- 是否触发 first packet。
- 是否触发 first decoded frame。
- 是否触发 first rendered frame。
- 是否进入 playing。
- 是否进入 buffering。
- 是否发生 seek。
- 是否切过清晰度。
- 是否重建过播放器。

### 6. 解码信息

需要回流：

- 使用硬解还是软解。
- 解码器名称。
- 解码器创建结果。
- 解码输入 packet 数。
- 解码输出 frame 数。
- 解码错误码。
- 首帧解码耗时。
- 解码平均耗时。
- 解码丢帧数。
- 解码队列长度。
- 是否发生 flush。
- 是否发生 decoder reset。
- 是否从硬解降级到软解。

### 7. 渲染信息

需要回流：

- 渲染引擎类型，例如 Surface、TextureView、Metal、OpenGL。
- 渲染 View 是否 attach。
- 渲染 View 尺寸。
- 首帧渲染耗时。
- 最近一次渲染时间。
- 渲染帧数。
- 渲染失败次数。
- Texture 创建状态。
- Surface 生命周期事件。
- 是否发生前后台切换。
- 是否发生横竖屏切换。
- 是否复用 View。
- 是否重新绑定渲染目标。

### 8. 用户操作信息

需要回流：

- 点击播放。
- 暂停。
- 恢复。
- seek。
- 切清晰度。
- 切线路。
- 倍速。
- 进入后台。
- 回到前台。
- 横竖屏切换。
- 页面退出。
- feed 滑动导致播放器复用。

很多黑屏问题只在某个操作序列后出现，比如“播放中切后台，回来后立刻 seek，再切清晰度”。没有操作序列很难复现。

## 四、分层排查方法

### 1. 资源层排查

#### 判断方法

先判断是否是资源本身有问题。

可以做以下对比：

- 同一视频在不同设备是否都异常。
- 同一视频在不同播放器是否都异常。
- 同一视频不同清晰度是否都异常。
- 同一视频不同 CDN 是否都异常。
- 下载到本地后用 ffplay、VLC、系统播放器是否异常。

#### 常见问题

- 源文件本身损坏。
- 转码输出文件损坏。
- 某个清晰度转码异常。
- HLS 分片缺失。
- M3U8 索引错误。
- MP4 moov box 异常。
- 关键帧间隔过大导致 seek 后黑屏。
- 编码 profile 或 level 超出设备支持范围。
- HDR/10bit 下发给不支持的设备。

#### 修复方式

- 重新转码。
- 下线异常资源。
- 屏蔽异常清晰度。
- 修复 M3U8 或分片。
- 对编码参数建立准入规则。
- 对高风险资源上线前自动验片。

### 2. 网络/CDN 层排查

#### 判断方法

检查异常是否集中在：

- 某个 CDN 厂商。
- 某个 CDN 节点。
- 某个地域。
- 某个运营商。
- 某类网络环境。
- 某些分片 URL。

#### 常见问题

- CDN 缓存了损坏分片。
- Range 请求返回内容不正确。
- CDN 回源失败。
- HTTP 206 返回异常。
- 下载内容被截断。
- 分片超时导致播放器拿到不完整数据。
- DNS 调度到异常节点。

#### 修复方式

- 刷新 CDN 缓存。
- 切换备用 CDN。
- 回源重新拉取。
- 降低异常节点权重。
- 客户端增加分片校验和重试。
- 对关键错误码触发 CDN fallback。

### 3. 容器/Demux 层排查

#### 判断方法

如果资源能下载，但播放器解析异常，需要看容器层。

关注：

- 是否能正常解析音视频轨。
- 时间戳是否连续。
- DTS/PTS 是否异常。
- 关键帧索引是否正确。
- seek 后能否找到有效关键帧。
- 音视频轨时长是否一致。

#### 常见问题

- PTS 回退。
- DTS/PTS 不连续。
- 音视频轨时长不一致。
- 关键帧索引缺失。
- HLS 分片 timestamp 不连续。
- fMP4 box 异常。

#### 修复方式

- 修复转码和封装流程。
- 客户端增强容错。
- seek 时对关键帧做保护。
- 对异常 timestamp 做兜底修正。

### 4. 解码层排查

#### 判断方法

核心问题是：解码器有没有正常输出视频帧。

可以看：

- decoder 是否创建成功。
- 输入 packet 是否正常送入。
- 输出 frame 是否持续产生。
- 输出 frame 的时间戳是否推进。
- 解码错误码是否出现。
- 切软解后是否恢复。
- 换 H.264 是否恢复。

#### 常见问题

- 硬解不支持当前编码参数。
- 解码器创建成功但输出异常。
- 解码器 flush 后状态未恢复。
- seek 后没有重新喂关键帧。
- 某些机型 MediaCodec/VideoToolbox 存在兼容性问题。
- H.265、HDR、10bit、B 帧等组合触发硬解 bug。

#### 修复方式

- 建立硬解黑名单。
- 特定机型切软解。
- 特定编码格式切 H.264。
- 解码失败后重建 decoder。
- seek 后等待关键帧再恢复渲染。
- 对不支持的 profile/level 做服务端过滤。

### 5. 渲染层排查

#### 判断方法

如果解码有输出，但屏幕异常，就看渲染层。

重点判断：

- video frame 是否送到 renderer。
- renderer 是否收到 frame。
- renderer 是否成功提交到 GPU。
- render view 是否可见。
- render view 尺寸是否正确。
- surface/texture 是否有效。
- shader 采样是否正确。
- YUV 格式是否匹配。

#### 常见问题

- Surface 被销毁但播放器还在渲染旧 Surface。
- Texture 被复用，导致显示旧数据或错误数据。
- View 尺寸为 0。
- 渲染层被业务 UI 遮挡。
- YUV 格式识别错误。
- UV 分量顺序错误。
- stride 未正确处理。
- 横竖屏旋转矩阵错误。
- 前后台切换后没有重新绑定渲染目标。

#### 修复方式

- 统一管理渲染 View 生命周期。
- Surface 销毁后暂停渲染，重建后重新绑定。
- 前后台切换后检查渲染目标有效性。
- 对 YUV 格式做明确分支处理。
- 对 stride、slice height、rotation 做兼容。
- 清晰度切换和 seek 后清理旧纹理。

### 6. 业务状态机排查

#### 判断方法

很多黑屏不是底层问题，而是业务状态和播放器状态不同步。

需要检查：

- 业务认为在播放，播放器是否真的在 playing。
- 播放器在 playing，View 是否真的可见。
- 页面销毁后播放器是否仍在渲染旧 View。
- cell 复用后播放器是否绑定到错误 View。
- 首帧回调丢失后业务是否一直显示 loading 或黑层。
- 暂停、恢复、seek、切清晰度是否有状态冲突。

#### 常见问题

- 状态机重复调用 prepare/play。
- seek 和清晰度切换并发。
- 页面退出时未解绑播放器。
- 列表复用中旧播放器覆盖新播放器。
- 首帧回调未到，业务一直遮罩。
- 业务 loading 层遮挡播放器。

#### 修复方式

- 播放器状态机单向流转。
- 关键操作串行化。
- 每次播放绑定唯一 playSessionId。
- View 复用时校验 session 是否匹配。
- 首帧超时后触发恢复策略。
- 页面退出时明确 detach renderer。

## 五、从现象到归因的决策树

### 1. 黑屏排查决策树

```text
黑屏
├─ 有声音吗？
│  ├─ 有声音
│  │  ├─ 解码有视频帧输出吗？
│  │  │  ├─ 有：查渲染 View、Surface、Texture、遮挡、尺寸、前后台
│  │  │  └─ 无：查解码器、视频轨、硬解兼容性
│  │  └─ 音频 clock 是否推进？
│  │     ├─ 推进：疑似有音无画
│  │     └─ 不推进：查状态机或缓冲
│  └─ 没声音
│     ├─ 网络请求成功吗？
│     │  ├─ 成功：查 Demux、解码、状态机
│     │  └─ 失败：查鉴权、CDN、网络
│     └─ 是否进入 prepared/playing？
│        ├─ 是：查首帧渲染
│        └─ 否：查起播链路
```

### 2. 绿屏排查决策树

```text
绿屏
├─ 切软解是否恢复？
│  ├─ 是：硬解兼容性问题，建立黑名单或降级
│  └─ 否：继续排查渲染和资源
├─ 同一资源所有设备都绿屏吗？
│  ├─ 是：查转码、色彩空间、资源内容
│  └─ 否：查机型、系统、GPU、播放器内核
├─ YUV dump 是否正常？
│  ├─ 正常：查 YUV 转 RGB、shader、纹理绑定
│  └─ 异常：查解码输出
```

### 3. 花屏排查决策树

```text
花屏
├─ 所有播放器都花屏吗？
│  ├─ 是：资源或转码问题
│  └─ 否：播放器解码或渲染问题
├─ 是否集中在某个 CDN？
│  ├─ 是：CDN 缓存或分片损坏
│  └─ 否：继续排查端上
├─ 是否集中在某些机型？
│  ├─ 是：硬解兼容性或 GPU 渲染问题
│  └─ 否：查资源、网络、播放器状态机
├─ seek/切清晰度后才出现？
│  ├─ 是：查 flush、关键帧、旧纹理清理
│  └─ 否：查解码和渲染链路
```

## 六、修复和规避策略

### 1. 客户端自愈

客户端应该具备异常自恢复能力，而不是只上报失败。

可选策略：

- 首帧超时后自动重试。
- 解码器异常后重建 decoder。
- 硬解失败后切软解。
- H.265 异常后切 H.264。
- 当前清晰度异常后切低清晰度。
- 当前 CDN 异常后切备用 CDN。
- 有音无画时重建渲染 View。
- 前后台回来后校验 Surface 是否有效。
- 渲染长时间无帧时触发 renderer reset。

需要注意：

- 自愈策略要有次数限制。
- 每次自愈都要上报原因和结果。
- 自愈成功也要记录，否则线上问题会被隐藏。
- 自愈失败要给用户明确兜底 UI。

### 2. 硬解黑名单和能力探测

硬解问题很常见，尤其在 Android 生态或特定 iOS 版本上。

黑名单维度可以包括：

- 机型。
- 芯片。
- 系统版本。
- 解码器名称。
- 编码格式。
- profile。
- level。
- 分辨率。
- fps。
- 是否 HDR。
- 是否 10bit。

策略：

- 命中黑名单时直接软解。
- 命中灰名单时优先低风险码流。
- 线上监控发现异常后动态下发配置。
- 对新机型通过灰度和能力探测逐步放量。

### 3. 服务端下发策略

服务端不要把所有码流都无差别下发给客户端。

可以根据设备能力做选择：

- 不支持 H.265 的设备下发 H.264。
- 不支持 HDR 的设备下发 SDR。
- 低端设备限制最高分辨率和码率。
- 黑名单设备屏蔽高风险 profile。
- 弱网下优先下发低码率档位。

### 4. 转码和验片治理

资源上线前应有自动化质量检查。

检查项：

- 文件是否可解封装。
- 音视频轨是否完整。
- 时长是否正确。
- 关键帧间隔是否合理。
- 分辨率、fps、码率是否符合规范。
- profile、level 是否符合设备兼容性要求。
- HLS/DASH 分片是否完整。
- 每个分片是否可解码。
- 是否存在大面积花屏、绿屏、黑屏。
- 多清晰度之间时间戳是否对齐。

### 5. 渲染生命周期治理

渲染链路要重点处理生命周期。

关键原则：

- View 创建后再绑定 renderer。
- View 销毁前先 detach renderer。
- Surface 销毁后不要继续渲染。
- Surface 重建后重新绑定。
- 前后台切换后校验渲染目标。
- 横竖屏切换后更新尺寸和旋转矩阵。
- 列表复用时校验 playSessionId。

### 6. 业务兜底

用户体验上不能长时间停留在黑屏或异常画面。

兜底方式：

- 显示重试按钮。
- 提供切清晰度入口。
- 提供切线路入口。
- 自动重试失败后提示用户。
- 对异常资源临时屏蔽。
- 对高失败率视频降级封面预览或提示稍后再试。

## 七、预警体系

### 1. 阈值预警

适合监控明显事故。

例子：

- 黑屏率超过 1%。
- 首帧失败率超过 2%。
- 解码失败率超过 0.5%。
- 某 CDN 播放失败率超过 3%。
- 某 App 版本播放失败率相比基线翻倍。

### 2. 趋势预警

适合发现缓慢恶化或局部异常。

例子：

- 某机型绿屏率相比过去 7 天上涨 300%。
- 某视频资源黑屏率在 10 分钟内持续升高。
- 某系统版本首帧耗时 P95 突然变高。
- 某 CDN 节点卡顿率显著高于其他节点。

### 3. 维度归因看板

报警后应该自动提供 Top 维度，而不是只给一个错误率。

看板应包含：

- Top 机型。
- Top 系统版本。
- Top App 版本。
- Top 播放器内核版本。
- Top videoId。
- Top CDN 节点。
- Top 编码格式。
- Top 解码器名称。
- Top 错误码。
- Top 网络类型。

这样可以快速判断问题类型：

- Top videoId 集中：资源问题。
- Top CDN 集中：CDN 问题。
- Top 机型集中：兼容性问题。
- Top App 版本集中：版本回归。
- Top 编码格式集中：编码参数或硬解问题。

### 4. 自动止损

预警后可以结合动态配置自动止损。

止损策略：

- 临时下线异常资源。
- 屏蔽异常清晰度。
- 降低异常 CDN 权重。
- 对异常机型关闭硬解。
- 对异常版本关闭高风险播放特性。
- 对异常编码格式切换备用码流。

在（一）里我们把端侧 Agent 的链路拆开，并论证了一件事：**Agent 工程能力，大量可以复用传统互联网既有的那些能力**——可观测性、灰度、A/B、缓存、降级熔断、性能 Profiling、状态机、错误归因、UI 生命周期、端上数据回流。

这一篇我们把视角收敛到一件事：**端侧体验优化**。

也就是用户真正能感知到的那部分：点下去多久出字、字是不是顺滑地流出来、中途打断会不会卡、没网还能不能聊、手机烫不烫、出错了有没有兜底。

如果你做过播放质量治理，会发现这两件事是同构的。播放体验看「首帧耗时、卡顿、黑屏、发热」，Agent 体验看「首字耗时、流式断点、无输出、功耗」。链路都是多环节的长链路，最终体验是每一环的叠加。所以这篇我会反复拿（一）的框架来对照，让你看到「复用」不是口号，而是具体动作。

## 一、先定义：端侧体验到底是什么

很多人一提「Agent 体验」就只看模型回答质量。但用户不在乎背后跑的是 Transformer 还是别的模型，他在乎的是：

- **点下去多久出第一个字**（首字延迟，TTFT / Time To First Token）
- **字是不是顺滑地流出来**（流式平滑度，有没有一顿一顿或整段闪一下）
- **中途能不能打断**（用户反悔了，Agent 还在喋喋不休）
- **出错时有没有兜底**（不是白屏、不是转圈圈到天荒地老）
- **没网 / 弱网还能不能聊**（离线可用性、隐私）
- **手机烫不烫、电掉得快不快**（功耗与发热）

这些才是「体验」。回答质量决定「好不好用」，上面这些决定「能不能用、用得爽不爽」。

把体验指标列成一张表，方便后面逐项优化：

| 体验维度 | 核心指标 | 类比播放 |
| --- | --- | --- |
| 首字延迟 | TTFT（首 token 耗时） | 首帧耗时 |
| 端到端 | 完整响应耗时 | 起播到播完 |
| 流式平滑 | token/s、断点次数 | 渲染帧率、卡顿次数 |
| 稳定性 | 首响失败率、中断率 | 起播失败率、卡顿率 |
| 可控性 | 用户打断率、放弃率 | 用户主动退出率 |
| 网络适应 | 弱网成功率、离线可用 | CDN 切换成功率 |
| 资源 | 内存峰值、功耗、温升 | 解码功耗、发热 |
| 隐私 | 敏感数据出端率 | —— |

注意最后两行（资源、隐私）在端侧尤其突出。播放也会谈解码功耗，但 Agent 把「内存峰值、功耗、温升」推到了前台；而「隐私 / 数据不出端」几乎是 Agent 独有的体验与合规命题。

## 二、首字延迟（TTFT）优化

TTFT 是用户对「快不快」的第一直觉。把链路拆开看：

```text
用户触发
  → 上下文组装（读历史、读设备状态、拼 system prompt）
  → 意图/Planning（这步要做吗？做几次？）
  → 第一个 token 生成（端侧推理 or 云端推理）
  → 首字上屏
```

每一段都能抠：

**1. 上下文组装要预算制。** 历史对话、设备状态、RAG 检索结果一股脑塞进去，token 越多、首字越慢。按（一）说的「上下文预算 + 最近 N 轮 + 摘要」裁剪，能把组装耗时和首 token 前的预处理耗时一起压下来。

**2. 轻量规划前置，减少云端往返。** 简单意图（开灯、查天气、跳转某个页面）完全可以在端侧用规则或小模型先判断，直接执行，根本不进大模型。只有当意图复杂、需要推理或联网时，才上云。这就是（一）讲的「端云协同」——**端侧能做的绝不联网**。

**3. 流式首包，别等完整响应。** 云端大模型是边生成边返回的（SSE / 流式接口）。客户端要「拿到第一个 token 就上屏」，而不是等整段生成完再显示。这点和播放的「首帧即渲染」完全一致。

**4. 模型与 Session 常驻。** 冷启动一个端侧推理引擎、加载模型权重，本身就要几百毫秒到一秒多。对高频场景，可以让模型/推理 Session 常驻内存（或挂起而不是销毁），下次触发直接复用。代价是内存占用，要做权衡（见第五节）。

说白了，TTFT 优化本质就三句话：能并行的并行、能前置的前置、能不联网的绝不联网：

```text
onUserTrigger:
    context = assembleContext(budget)          # 预算裁剪，别全塞
    intent = localLightweightPlan(context)     # 端侧先判断意图
    if intent.isSimple:
        executeLocally(intent)                 # 简单意图，端侧直接做，零云端延迟
        return
    stream = callCloudModelStream(context)     # 复杂意图才上云，且流式
    renderFirstTokenAsSoonAsArrive(stream)     # 首 token 一到就上屏
```

## 三、流式输出体验

首字出来只是开始，用户会一直盯着后面怎么流。

**1. 增量渲染，不要整段替换。** 很多初版的 bug 是：每收到一个 token，就把「已有文本 + 新 token」整体 set 一次。文本长了之后，整体重渲染会闪、会卡。正确做法是维护一个增量缓冲，只追加新到的片段（SwiftUI 里就是绑定一个 `@State` 文本，token 到来时 `text += newPiece`，框架只 diff 变化部分）。

**2. 处理背压（backpressure）。** 模型产出可能比 UI 渲染快（尤其本地小模型吐字飞快）。直接全灌进 UI 会卡顿。加一个渲染节流：固定节奏（比如每 16~30ms）把缓冲里的 token 刷一次到界面，像播放器的「帧率」一样平稳。token 速率对应播放的「渲染帧率」。

**3. 可打断是基本功。** 用户看到 Agent 跑偏了，应该能立刻打断。这要求 in-flight 的请求能被取消：async Task 取消、URLSession 取消、端侧推理循环检查取消标志。打断后要及时清理渲染目标和会话状态，不能「嘴上停了、后台还在跑、内存还在涨」。

**4. 把「思考」和「工具调用」显性化。** Agent 在背后调工具、做 Planning 时，界面不能一片死寂（用户以为卡了）。用「正在思考…」「正在查天气…」这样的中间态，既是体验，也是遮丑——把等待变成可感知的进度。

## 四、端侧推理性能与功耗

这是端侧 Agent 和纯云端 ChatBot 最大的不同：**推理发生在用户的手机上**，就要吃手机的 CPU/GPU/NPU、内存、电池。

**1. 推理引擎与量化。** 端侧模型通常用 Core ML / MLX（Apple 平台）、或 ONNX Runtime / llama.cpp 等。模型做 int8 / int4 量化后，体积和算力需求大幅下降，速度更快、更省电。代价是精度略有损失，要在「快」和「准」之间取舍。

**2. 用对硬件：ANE 优先。** Apple 平台上有 Neural Engine（ANE），专门跑神经网络，比用 GPU/CPU 推理**省电得多**。能用 ANE 就别用 GPU，能用 GPU 就别用 CPU——这点对应播放里的「硬解（MediaCodec/VideoToolbox）优先于软解」。同样是解码/推理，走专用硬件，功耗和发热都更优。

**3. 内存与冷启动的权衡。** 模型常驻内存 → 首字快，但占内存、可能被系统回收；按需加载 → 省内存，但冷启动慢。移动端内存紧张（尤其老机型），这里要做分级：高频入口常驻、低频能力懒加载。和播放的「解码器创建」是一个取舍。

**4. 长会话的发热治理。** 连续长时间推理会触发系统温控降频，一旦降频，推理变慢、体验劣化、更烫，恶性循环。策略：长任务分批跑、闲时再跑重活、优先 ANE、必要时主动降级到云端（把发热甩给服务器）。这其实就是播放「长时间解码发热」的同一类问题。

## 五、弱网与混合部署体验

端侧 Agent 经常要在「网络不好」的环境里工作，所以「端云协同」不是性能优化，也是体验优化。

**1. 能力分级，能端侧就端侧。** 把能力分成三档：纯端侧（规则/本地模型，零网络）、端云混合（本地规划 + 云端大模型）、纯云端（复杂推理）。默认走最左档，只在必要时右移。这样无网时至少基础能力可用。

**2. 弱网降级。** 云端请求超时 / 失败，不要转圈到死。降级策略：切备用线路 → 退回端侧小模型 → 退回本地规则答案 → 明确提示「当前网络不佳，已切换为离线模式」。对应播放的「CDN 切换 + 软硬解降级 + 超时兜底」。

**3. 流式恢复，不丢上下文。** 网络从 Wi-Fi 切到蜂窝、或从地库出来，正在进行的流式回答可能断。好的体验是：Session 不丢、已生成的部分保留、恢复后从断点继续，而不是从头再来。这里 `agentSessionId` 就要贯穿网络切换，和播放的 `playSessionId` 跨前后台/切 CDN 是同一思路。

**4. 离线优先。** 设计上默认「能离线」：本地模型兜底、本地缓存常用知识、敏感数据不上云。离线能力既是体验（地铁里也能用），也是隐私（数据不出端）。

## 六、UI 生命周期与状态机（直接复用播放治理）

这一节几乎可以照抄播放质量治理，因为坑一模一样：列表复用、前后台、横竖屏、页面退出。

**1. 状态机单向流转。** Agent 的 UI 状态建议是这样：

```text
idle → thinking → streaming → done
                 ↘ error
streaming → interrupted（用户打断）
```

关键操作和播放一样：**单向流转、关键操作串行化、每次会话绑定唯一 `agentSessionId`**。

**2. 列表 / 页面复用要校验 Session。** Feed 流里多个卡片各有自己的 Agent，或者页面 push/pop 后播放器复用——这些场景如果 Session 没绑定对，就会出现「A 的回答渲染到 B 的 View 上」的错乱。渲染前先校验 `agentSessionId` 是否匹配当前 View，不匹配就拒收。这和播放器「View 复用校验 playSessionId」是完全一样的防错手段。

**3. 生命周期事件要管好渲染目标。** 页面退出 → detach 渲染目标；进入后台 → 暂停/挂起推理；回到前台 → 校验渲染目标还是否有效（Surface/Texture 类比）；横竖屏 → 更新尺寸与布局。任何一步漏了，都会出现「后台还在跑、回来黑屏、内存泄漏」。

## 七、降级与兜底（端上自愈）

把第六节和第五节串起来，就是端侧 Agent 的「自愈」能力——出错不要只上报，要能自己恢复：

- 首字超时 → 自动重试 / 切线路
- 端侧推理异常 → 切云端大模型
- 云端超时 → 退回端侧小模型 / 本地规则
- 生成中断 → 从已输出部分恢复，或提示重试
- 弱网 → 切离线模式

但要注意（和播放自愈一样的三条铁律）：

1. **自愈要有次数上限**，否则无限重试反而更糟。
2. **每次自愈都要上报原因和结果**——自愈成功也要记，否则线上问题被「悄悄修好」而无人知晓。
3. **自愈失败要给用户明确兜底 UI**（重试按钮、切清晰度/切线路入口），不能一直转圈。

## 八、可观测性：把体验变成可度量

优化不能靠「我觉得快了」，要靠度量，而且要按维度拆。

**核心指标**（对应第一节的表）：TTFT、端到端耗时、token/s、首响失败率、中断率、用户打断率、放弃率、弱网成功率、内存峰值、功耗、温升、敏感数据出端率。

**按维度聚合**，否则全局平均值会掩盖问题：

| 维度 | 能发现的典型问题 |
| --- | --- |
| 机型 / 芯片 | 某机型 ANE 支持差 → 功耗高、TTFT 慢 |
| 系统版本 | 某 iOS 版本推理 API 回归 |
| 模型版本 | 新量化模型精度下降、吐字变慢 |
| 网络类型 | Wi-Fi 快、蜂窝下弱网降级频繁 |
| 是否走 ANE | ANE 路径 vs GPU 路径功耗差异 |
| 是否云端 | 云端链路 RT 高、弱网失败多 |

**预警**同样用阈值 + 趋势：TTFT P95 超过 X ms、某机型放弃率上涨 300%、某模型版本 token/s 下降 20%，都该自动报警。

你会发现，这和（一）里说的「播放质量可观测性 + 维度归因 + 预警」是同一套方法论，只是指标名换了。

## 九、一张表收口：传统能力 → 端侧体验优化

把（一）的 10 项可复用能力，映射到本篇的具体体验动作，方便你建立肌肉记忆：

| 传统能力（一） | 在端侧体验优化里的具体动作 |
| --- | --- |
| 可观测性 / Tracing | 埋 TTFT、token/s、中断率、功耗，串 `agentSessionId` |
| 灰度 / Feature Flag | 新模型、新推理引擎、新降级策略先灰度量级放开 |
| A/B 实验 | 对比 ANE vs GPU、量化档位、流式节流节奏对体验的影响 |
| 缓存 / CDN | KV cache 命中、会话级上下文缓存、常驻 Session |
| 重试 / 降级 / 熔断 | 端侧→云端→规则的多级兜底，弱网切离线 |
| 性能 Profiling | 拆解 TTFT 各环节耗时，定位是组装慢还是推理慢 |
| 状态机 | idle→thinking→streaming→done 单向流转 |
| 错误归因 | 按机型/模型/网络维度定位体验劣化根因 |
| UI 生命周期 | 前后台 / 横竖屏 / 列表复用时校验 Session、管好渲染目标 |
| 端上数据回流 | 一次会话全链路数据可回放、可归因 |

## 结尾与预告

这一篇我们讲了端侧体验优化：从首字延迟、流式平滑、推理功耗，到弱网混合部署、UI 生命周期、自愈兜底，最后用可观测性把一切变成可度量。核心结论是——**这些都不是 Agent 时代的新发明，而是传统互联网工程能力在端侧推理场景下的重新落地**。

但有一类问题前面一直绕着走：**Agent 的生成是不可控的**。同样的输入，模型可能给出结构不同的回答；要它输出 JSON 它可能带废话；要它调用工具它可能调错；长任务它可能跑偏。这些「生成可控性」问题，才是 Agent 能不能上生产的关键。

下一篇（三）我们就专门讲：**AI Agent 生成是不可控的，如何让生成符合预期**——约束解码、结构化输出、Tool Calling 可靠性、Plan 校验、回滚与重规划、以及用传统测试/回归的思路做 Agent 质量保障。

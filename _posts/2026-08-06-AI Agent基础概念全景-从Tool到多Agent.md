title: AI Agent 基础概念全景：从 Function Calling 到多 Agent
---

写系列（一）到（四）的时候，MCP、Tool、Skill、Agent、Workflow 这些词反复冒出来。它们都和「扩展 Agent」有关，但不在同一层——不先分清楚，讨论端侧怎么落地就会各说各话。这篇是我自己理清它们关系的笔记，先把坐标摆正，再回看系列会顺很多。

它们第一次被塞进同一句话，通常是这样的：「接个 Agent，搞个 Workflow，再上 MCP，能力不够配几个 Skill。」那句话里，车、发动机、司机、高速、GPS 全混在一起——车是整车，发动机是零件，司机是角色，高速是路径，GPS 是工具，混着说当然乱。

我的分法是两层：**Tool / Skill / MCP 是能力原语**（Agent 手里的家伙什）；**Agent / 多 Agent / Workflow 是执行形态**（谁来决定下一步做什么）。分两层，世界就清爽了。

## 一、能力原语：Agent 手里的家伙

这组最容易混，因为它们都在「扩展 Agent 能力」上，但处在不同层。先讲最底层、也最容易被漏掉的 **Function Calling**——它没写进那句需求，却是 Tool / Skill / MCP 能成立的前提。

### Function Calling：让模型「开口要调函数」的机制

给模型一批函数的 schema（名字、参数、描述），模型生成时如果觉得该调某个函数，就吐一段结构化请求而不是自然语言：「我要调 `get_weather`，参数是 `{city: "北京"}`」。程序解析它、真正执行、把结果喂回去，模型接着生成。一个会话里往往来回好几轮。

Function Calling 是**机制（动词）**，Tool 是那个**被调的函数（名词）**。没这个机制，Tool 就是一堆死定义；有了它，Tool 才被模型驱动起来。

### Tool：Function Calling 落地的具体函数

Tool 就是带 schema 的函数。它正是 Function Calling 里被调用的那个函数。原子、单一动作，模型自己决定这步调哪个。

例子：`get_weather(city)`、`github_create_issue(title, body)`、MCP 暴露的任何一个 tool。我博客里写的 `BabyFoodTool` / `ReminderTool`（带 schema + parser 强校验）就是典型 Tool——两层校验的打法在系列（三）展开过。

### Skill：用 Tool 搭出来的成品

Skill 是更高层的能力包：一套指令 + 串起多个 Tool + 领域知识 + 异常处理。「生成 PDF 报告」「评审一个 PR」「部署到预发」都算。

Skill 建在 Tool 之上。Tool 是积木，Skill 是用积木搭的成品。Tool 直接进模型的可调用清单，模型逐次决策；Skill 更像把一套打法加载进上下文，省下模型临时拼装的成本，也把零散 Tool 收成一个语义清晰的能力。在 WorkBuddy 里，Skill 就是一个 `SKILL.md` 打包的能力包，用到时加载进来告诉 Agent 工作流怎么走。

### MCP：把 Tool 接到外部系统的标准接口

MCP（Model Context Protocol）是 Anthropic 在 2024 年底开源的协议，给 AI 应用和外部世界（工具、数据、提示模板）之间定一个标准接口。

它不发明新能力——它暴露的 Tools 本质就是 Function Calling 的函数，只是不住在调用方进程里，而住在一个独立 MCP Server 进程/服务里，由 JSON-RPC 2.0 跨进程调用。**MCP ≈ Function Calling 的跨进程标准化版。**

```text
AI 应用 (Host)
   │ 内嵌 MCP Client，JSON-RPC 2.0
   ▼
MCP Server (独立进程/服务，对接真实后端)
   │
   ▼
真实系统：GitHub / 数据库 / 文件系统 ...
```

传输用 stdio（本地，Server 是本地子进程）或 HTTP/SSE（远程，Server 跑在别处）。MCP Server 暴露三类原语：**Tools**（可调用的函数）、**Resources**（可读取的数据）、**Prompts**（可复用模板）。

什么时候值得上 MCP：一个外部系统要被多个 AI 应用连接（写一次 Server 全接）、集成本身不简单（鉴权/有状态/多步）、想被生态复用。如果只是单一 App、单一模型、集成简单，原生 Function Calling 把 Tool 写在自己进程里就够，不必引进程边界和协议开销。

#### MCP 在移动端合适吗

它的核心价值——标准化、可插拔、N+M 解耦——主要是服务端、桌面、云的故事。在单个已上架的移动 App 里，它通常不是默认答案，但要分场景看。

不适合的情况：

- **纯端侧、离线、本地 Tool**。iOS/Android 沙盒严格限制多进程和后台进程，经典 stdio MCP Server（拉起子进程）在手机上基本不成立；更要命的是它废掉了「弱网降级 / 离线可跑」这个卖点——一旦必须连一个 MCP Server，离线就废了。这种场景用原生 Function Calling + 进程内 Tool 最干净，就像我的 `LocalLLMDemo` 现在做的。
- **只有一个 App、只接一两个自家后端**。N+M 解耦的红利吃不到，反而背上协议和传输开销。

适合的情况——前提是「云侧」那一半：

- **云端把自家后端能力以 MCP 暴露，手机作为瘦客户端用 HTTP/SSE 去调**。这时手机跑的不是 Server，而是 MCP Client——很轻，只是发 JSON-RPC 请求。这正好接上系列（四）的端云结合：本地 Tool 进程内直跑（Function Calling），云端重 Tool 走 MCP。
- **iOS / Android / Web 多端共用同一套后端 Tool 契约**：放云端定义成 MCP，三端共用一份 schema，一致性白捡。

我的判断：移动端适合当 MCP Client 连云端 Server，不适合在手机里跑 MCP Server。本地活交给 Function Calling，跨进程/跨网络的活才交给 MCP。

### 一条调用链看清四个词

孤立记这四个词没用，看一次真实请求怎么流过去：

```text
用户：「北京天气怎样？顺便算 23*7」
   │
   ▼
① LLM（带着 Tool 的 schema 列表）          ← Function Calling（机制）：模型决定「调谁」
   │  输出：function_call { get_weather, {city:"北京"} }
   ▼
② Agent 循环 解析出函数名+参数             ← 调用方程序（AgentLoop）
   │
   ▼
③ 查 ToolRegistry 找到 get_weather          ← Tool（名词）：被调的函数
   │
   ▼
④ 执行：本例是进程内函数                    ← Function Calling 落地
        （若是云端重活，这一步改成 MCP Client → 远程 MCP Server）
   │                                         ↑ 这里就是 MCP 的位置（跨进程那一下）
   ▼
⑤ 把结果「北京 25℃ 晴」喂回 LLM
   │
   ▼
① LLM 再决定调 calculator{"23*7"} → ③ ④ ⑤ → 最后输出自然语言答案
```

这组关系串起来就是：Function Calling 是机制（模型怎么开口要调），Tool 是那个被调的函数，Skill 是把多个 Tool 编排成的成品能力，MCP 是 Tool 不住本进程时跨进程接进来的标准接口。

我用 iOS 开发的习惯类比一下，好记：

- **Function Calling** ≈ Objective-C 的消息派发——编译期不知道调哪个方法，运行时（模型）根据名字+参数临时决定。
- **Tool** ≈ 被派发到的那个方法实现（`- [UserService fetchProfile:]`）。
- **MCP** ≈ 给后端能力定义标准协议 + 常驻服务（USB-C 化），任何客户端不必写私有 SDK 就能调。
- **Skill** ≈ App 里的「功能模块 / 业务流程」（比如「下单」），内部依次调多个方法还处理异常兜底。

## 二、执行形态：谁来决定下一步

### Agent：自驱的执行者

我在系列（一）里给 Agent 下的定义：能自己决定「下一步做什么」并调用工具去做的程序，不是问一句答一句的问答机器人。

```text
普通对话：输入 → 模型 → 输出（结束）
Agent：    输入 → 模型(决定调哪个工具) → 执行工具
        → 拿到结果 → 模型(再决定) → ... → 输出
```

核心就两个字：**自主**。给目标，它自己拆步骤、自己调 Tool、自己看结果再决定，直到完成或到停止条件。我的 `LocalLLMDemo` 里那个 `generate` 循环，就是单 Agent 的心脏。

一个东西算不算 Agent，看这几条齐不齐：有目标、能用 Tool、跑循环（多步自驱）、有状态/记忆、能自己停。

### 多 Agent：分而治之的团队

一个 Agent 啥都干，会出三个毛病：prompt 巨大、上下文被各种任务污染、没法专精。多 Agent 就是拆成多个各司其职的专员协作。

常见形态：

- **编排者 / 路由器**：一个「组长」Agent 判断派给哪个专员（像 team lead）。
- **流水线**：A → B → C 顺序交接（研究员交给写手交给审校）。
- **协作 / 辩论**：一个提方案、一个挑刺、一个综合，用对抗换质量。
- **共享黑板**：多个 Agent 读写同一份状态。

什么时候上多 Agent：任务复杂能分工专精、子任务能并行、需要上下文隔离（不同 Agent 各管各的窗口）、不同子任务想用不同模型/Tool。简单任务硬上是过度设计——协调开销、延迟、成本全上去，单 Agent + 好 Tool + Skill 往往就够了。

### Workflow：写死步骤的编排骨架

它最容易被和 Agent 搞混，区别在**「谁来决定步骤顺序」**：

- **Agent**：步骤是模型运行时临时决定的（自驱循环）→ 灵活，但不可完全预测。
- **Workflow**：步骤是开发者事先写死的（声明式 DAG / 状态机）→ 顺序固定，模型最多在固定节点「填空」。

```text
Workflow（顺序写死）：
  步骤1 总结文档 → 步骤2 翻译 → 步骤3 发 Slack
  （每步可能调 LLM 或普通服务，但「先总结再翻译再发」是写死的）

Agent（模型临场决定）：
  给目标 → 模型自己判断先查哪、再调谁、要不要重试 ...
```

Workflow 更像传统的业务流程编排（LangGraph 的图、Temporal、n8n、Dify 的流程，本质都是 DAG）。LLM 在 Workflow 里只是某个节点上的一个动作，不是总指挥。

什么时候用 Workflow：路径明确、要可复现、要 debug 友好、要便宜可控——稳定生产管线。什么时候用 Agent：路径不确定、要应对未知、要临场发挥。现实里大量系统是**混合**的：Workflow 里嵌 Agent 节点（agentic workflow）。别被「Agentic」宣传忽悠——诚实地问一句：步骤是写死的还是模型选的。

iOS 开发的习惯类比这一组：

- **Agent** ≈ 能自己跑完用户意图的独立服务/模块，内部有循环（读状态→决策→调接口→看结果→再决策），不用一步步指挥。普通 API 调用 / ChatBot = 调一次返一次，没有「自己接着干」的循环。
- **多 Agent** ≈ 微服务架构里多个各司其职的服务，由编排服务或消息总线协调，而不是一个巨无霸服务什么都干。
- **Workflow** ≈ 开发者写的固定业务流程/状态机（「下单流程」：校验→锁库存→支付→发通知），每步可能调 LLM 或普通服务，但顺序写死，不是 LLM 临场决定。

## 三、总图：把六个数在同一张图上

两组合起来，就是完整的坐标系：

```text
                    ┌─────────────────────────────┐
                    │  Workflow / Orchestrator    │  ← 编排者（固定或动态协调）
                    └──────────────┬──────────────┘
            ┌──────────────────────┼──────────────────────┐
            ▼                      ▼                      ▼
      ┌──────────┐          ┌──────────┐          ┌──────────┐
      │ Agent A  │          │ Agent B  │          │ Agent C  │  ← 执行形态（自驱）
      │ (专做 X) │          │ (专做 Y) │          │ (审核)   │
      └────┬─────┘          └────┬─────┘          └────┬─────┘
           │ 用 Tool1/Tool2      │                     │
           │ + Skill α           │                     │
           │ 经 MCP 接系统        │                     │
           └─────────────────────┴─────────────────────┘
                    ▲
                    │
           ┌────────┴────────┐
           │ 能力原语层        │  ← Function Calling（机制）/ Tool（积木）/ Skill（成品）/ MCP（接口）
           └─────────────────┘
```

对应关系：

- **Tool** = 原子动作，Agent 在循环里调它。
- **Skill** = 用 Tool 搭出来的成品能力。
- **MCP** = Tool/数据 连到 Agent 的标准接口（水管）。
- **Workflow** = 写死步骤的编排骨架（脚本/状态机）。
- **Agent** = 自驱执行者，用 Tool（常经 MCP）+ Skill 跑闭环。
- **多 Agent** = 多个 Agent 由 Workflow/Orchestrator 协调，分而治之。

## 四、一个判断尺

全篇压成一句我随时会问自己的话：

> **「下一步谁决定？」**
>
> - 我写死的 → **Workflow**
> - 模型临场选的 → **Agent**
> - 多个模型各自选、有人协调的 → **多 Agent**

Function Calling / Tool / Skill / MCP 不抢「决定权」——它们是 Agent 和 Workflow 手里用的家伙什：Function Calling 是「模型怎么开口要调函数」的机制，Tool 是那个被调的函数（积木），Skill 是用积木搭的成品，MCP 是把积木接到外部系统的标准水管（当函数不住在本进程时）。

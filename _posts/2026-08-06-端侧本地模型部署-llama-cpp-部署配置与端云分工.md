> 这是「移动端 AI Agent 系列」的**部署实战篇**。
>
> （一）讲了端侧 Agent 的链路和传统能力的复用；（二）讲了端侧体验优化。那两篇偏「认知与体验」。这一篇偏「落地」：**本地模型到底怎么跑起来、怎么配置、怎么判断设备能不能跑、以及什么该放端侧什么该放云端**。
>
> 关键词是 **llama.cpp**——它是目前端侧本地推理事实上的标准引擎。

## 为什么要聊 llama.cpp：它「快」在哪

本地 run 模型，llama.cpp 确实是当下最快、最省心的一条路之一。它「快」和「轻」不是玄学，来自几个工程选择：

- **纯 C/C++，零 Python 运行时**：没有 PyTorch / Transformers 那套几百 MB 的依赖和解释器开销，启动快、内存小。
- **GGUF 单文件格式**：权重、tokenizer、元数据全打进一个文件，加载简单、跨平台（macOS / Linux / Windows / Android / iOS 通吃）。
- **量化是原生的**：int4 / int8 量化权重直接推理，体积和算力需求大幅下降，这是端侧能跑大模型的前提。
- **自动硬件探测**：启动时会检测 CPU 指令集（AVX2/AVX512/NEON）和可用 GPU，自动选最优执行路径和量化 kernel。
- **GPU offload 混合推理**：可以把一部分层卸载到 GPU（Apple 上是 Metal，NVIDIA 是 CUDA，AMD 是 ROCm，通用是 Vulkan），其余留 CPU，灵活适配硬件。
- **KV cache 量化 + Flash Attention**：长上下文下大幅省内存、提速度。

它把「在普通设备上跑 LLM」从研究玩具变成了可工程化的能力。下面直接上手。

## 一、快速上手：本地模型怎么跑起来

先明确一个事实：**llama.cpp 自己不提供模型文件**，需要先拿到一个 GGUF 格式的模型（从 Hugging Face 的 `unsloth`、`ggml-org`、`Qwen` 等仓库下载，或用 `huggingface-cli` / `modelscope` 拉取）。

拿到模型后，llama.cpp 提供一组命令行工具（2026 年的命名，旧名 `main`/`server` 是别名）：

| 工具 | 用途 |
| --- | --- |
| `llama-cli` | 交互式/一次性文本生成，本地调试首选 |
| `llama-server` | 起一个 **OpenAI 兼容**的 HTTP 服务（`:8080`），App 当 API 调 |
| `llama-bench` | 跑性能基准，测这台机器的 tokens/s |
| `llama-run` | 带「自动拉取模型」的runner，适合脚本/自动化 |
| `llama-quantize` | 把模型量化成更小的 GGUF（自己压模型用） |
| `llama-perplexity` | 测模型质量（困惑度） |

**1）交互式跑起来（调试用）**

```bash
llama-cli -m ./models/Qwen3-4B-Q4_K_M.gguf -cnv
```

`-cnv` 启用对话模板，进入聊天模式；直接退出用 `/bye`。

**2）起一个本地 API 服务（App 集成用）**

```bash
llama-server -m ./models/Qwen3-4B-Q4_K_M.gguf \
  --host 0.0.0.0 --port 8080 \
  -c 8192 -ngl 99 -fa on
```

起来后，App 端直接调 OpenAI 格式的接口：

```bash
curl -X POST http://localhost:8080/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"local","messages":[{"role":"user","content":"用一句话解释注意力机制"}],"max_tokens":256}'
```

**3）用 `llama-run` 一键跑（自动下载）**

```bash
llama-run hf.co/Qwen/Qwen3-4B-GGUF:Q4_K_M "解释一下梯度下降"
```

`llama-run` 会从 Hugging Face 自动拉取指定量化的 GGUF，省去手动下载。适合写脚本、做 Demo。

> 移动端（iOS/Android）则是把 llama.cpp 编译成库嵌进 App，用它的 C API 做 in-process 推理；iOS 上也可选 Apple 官方的 Core ML / MLX 路线（Core ML 可让部分层走 ANE 更省电）。**但要提醒：llama.cpp 的 `-ngl` 卸的是 Metal/GPU，不是 ANE**——ANE 要走 Core ML 后端那条独立路线，且对 LLM 收益有限。**「能不能跑、怎么配置、端云怎么分」的判断逻辑完全一致**，下面这套都适用。

## 二、本地模型怎么配置：关键参数逐一看

「本地 run 很快」的前提是**配置对**。核心就这几个旋钮：

### 1. 选模型 + 量化（最重要的一步）

量化等级决定了「体积 / 速度 / 精度」的取舍。经验值（每参数字节数 → 7B 模型大小 → 质量保留）：

| 量化 | 字节/参数 | 7B 大小 | 质量保留 | 建议 |
| --- | --- | --- | --- | --- |
| Q8_0 | ~1.06 | ~8.5 GB | ~99.5% | 不差钱、要精度 |
| Q6_K | ~0.81 | ~6.3 GB | ~99% | 精度敏感 |
| **Q4_K_M** | **~0.55** | **~4.7 GB** | **~95%** | **甜点，大多数场景首选** |
| Q3_K_M | ~0.43 | ~3.9 GB | ~90% | 内存紧 |
| Q2_K | ~0.31 | ~3.0 GB | ~85% | 勉强跑 |
| IQ3 / IQ2 | 更低 | 更小 | 比同级 Q 好 | 极限压缩、塞小设备 |

**结论**：端侧默认从 **Q4_K_M** 起步；塞不下再降，但要注意 **Q4 以下推理/代码类任务质量滑坡明显**。塞得下就别硬压——一个更小的模型用高量化，往往比一个大模型压成渣更好（比如 8B@Q8 通常比 70B@Q2 又快又准）。

**参数规模 ↔ 设备档位** 的粗略映射：

- **手机（4~12GB RAM）**：1B~3B 为主，上下文 2K~4K。再大就扛不住。
- **笔记本 / 桌面（16~32GB）**：7B~13B Q4 很舒服，上下文 8K。
- **Mac（64GB 统一内存）**：可上 70B Q4——这是 Apple Silicon 的杀手锏（见下）。
- **服务器（多卡）**：34B~70B+，高并发。

### 2. 上下文窗口 `-c / --ctx-size`

决定 KV cache 多大（直接影响内存，见第三节）。对话/摘要短任务 4K~8K 足够；RAG、长文档才需要 32K+。**上下文不是越大越好，它线性吃内存**。

### 3. 线程数 `-t / --threads`

CPU 推理的并行度。一般设成**物理核心数**；Apple/ARM 的大小核架构下，设成性能核数量更稳。llama.cpp 默认也会按 CPU 探测给个值。

```bash
llama-cli -m model.gguf -t 8 -c 4096
```

### 4. GPU 卸载层数 `-ngl / --n-gpu-layers`

这是「快」的关键开关：**把多少层放到 GPU 上算**。设 `99` 表示尽量全卸载。

- 有 Metal/CUDA/Vulkan → 设大（`-ngl 99`），推理飞快、省电。
- 纯 CPU → 设 `0`，否则它会尝试 offload 失败反而慢。

```bash
llama-server -m model.gguf -ngl 99 -c 8192 -fa on
```

> ⚠️ 用 `--verbose` 看日志，确认有没有 `offloading N layers to GPU`。如果出现 `offloading N layers to CPU`，说明 `-ngl` 没生效或显存不够——这是「配置错了但看起来在跑」最常见的坑。

> 再强调一次：**这里的「GPU」在 Apple 上是 Metal/GPU，不是 ANE**。llama.cpp 的 Metal 后端不碰 ANE；想用 ANE 得走 Core ML 转换路线（见上）。日常跑 LLM，老老实实用 Metal/GPU 就是最快最稳的选择。

### 5. Flash Attention `-fa on`

开启后长上下文**内存更小、速度更快**。几乎所有新模型都建议开。

### 6. KV cache 量化 / 分页

KV cache 默认按 FP16 存（见下节公式）。可以用 `--kvq` 之类参数把 KV 也量化（如 int8），长上下文下再砍一半内存，精度损失很小。llama.cpp 也支持分页 KV，避免长会话 OOM。

### 一个完整配置示例（16GB Mac 跑 7B）

```bash
llama-server \
  -m ./models/Qwen3-7B-Q4_K_M.gguf \
  -c 8192 \        # 上下文 8K
  -ngl 99 \        # 全卸载到 Metal
  -fa on \         # Flash Attention
  -t 8 \           # 8 线程
  --host 0.0.0.0 --port 8080
```

## 三、内存与 CPU 信息收集：哪些指标用来判断「能不能本地部署」

这是前面专门问的点，也是端侧部署最容易翻车的地方——**纸面参数看着能跑，真机一跑就 OOM / 卡死**。所以要先采集设备能力，再决定能不能上本地模型。

### 1. 设备「画像」该采集什么

| 采集项 | 为什么重要 | 用于判断 |
| --- | --- | --- |
| **系统总内存 & 可用内存（RAM）** | 最硬的指标。模型权重+KV cache 必须装得下 | 模型规模上限 |
| **SoC / 芯片型号** | 决定 NPU、内存带宽、统一内存大小 | 档位划分 |
| **CPU 架构 / 指令集**（NEON/AVX2/AVX512） | 影响 CPU 推理速度 | 纯 CPU 是否可行 |
| **GPU/NPU 能力**（Metal / ANE / NNAPI / Vulkan） | 能否 offload、是否省电 | `-ngl` 设多少、功耗 |
| **可用存储** | GGUF 文件几 GB，低端机空间紧张 | 能否下发模型 |
| **系统版本** | 影响 NPU 推理 API 可用性 | 是否启用端侧 |
| **功耗/温控历史** | 长时间推理会触发降频 | 能否持续跑 |

### 2. 内存账怎么算（最核心的公式）

本地部署的内存 = **模型权重 + KV cache + 系统/App 开销**。权重看量化，KV cache 用公式：

```text
KV_cache_bytes = 2 × n_layers × n_kv_heads × head_dim × seq_len × bytes_per_elem
```

- `2`：Key 和 Value 两份
- `n_kv_heads`：GQA 之后的 KV 头数（远小于 query 头数，这是现代模型能跑长上下文的关键）
- `head_dim`：一般 128
- `bytes_per_elem`：KV cache 默认 **FP16（2 字节）**，哪怕权重是 Q4——量化只压权重，KV 默认不压
- `seq_len`：上下文长度

**算两个常见模型的「每 token KV 占用」：**

- **Llama-3.1-8B**：32 层，8 KV 头，head_dim 128 → `2×32×8×128×2 = 131072 B ≈ 0.125 MB/token`
  - 4K → ~0.5 GB，8K → ~1.0 GB，32K → ~4 GB，128K → ~16 GB
- **Llama-3.1-70B**：80 层，8 KV 头，head_dim 128 → `2×80×8×128×2 = 327680 B ≈ 0.3125 MB/token`
  - 4K → ~1.25 GB，32K → ~10 GB，128K → ~40 GB

**一个实际判断例子**（16GB Mac 跑 8B Q4_K_M，上下文 8K）：

```text
权重    ≈ 4.9 GB   (8B × 0.55)
KV cache≈ 1.0 GB   (0.125 MB/token × 8192)
开销    ≈ 2~3 GB   (macOS + App)
合计    ≈ 8 GB  <<  16GB 统一内存（可用约 12GB）
→ 装得下，且宽松。✅
```

**手机例子**（6GB RAM，App 可用约 2GB）：

```text
3B Q4 权重 ≈ 2.0 GB
KV(4K)    ≈ 0.25 GB
合计      ≈ 2.25 GB  ≈ 2GB 可用  → 顶满/易 OOM ⚠️
→ 手机端侧通常只能上 1B~3B 且小上下文，或量化更狠。
```

> **Apple Silicon 的特殊性**：它用「统一内存」，CPU 和 GPU 共用一块池子、零拷贝。所以一台 64GB 的 Mac 能直接把 70B Q4（~40GB 权重）整个塞进内存，而这在独显上要两张 24GB 卡。**但代价是内存带宽决定了解码速度**—— Mac 带宽不如高端 GPU，所以「能装下」≠「跑得快」。

### 3. 别只信纸面：用 `llama-bench` 真机跑

参数算得再好，也不如真机实测。在目标设备上跑：

```bash
llama-bench -m ./models/Qwen3-4B-Q4_K_M.gguf -c 4096 -ngl 99
```

它会输出两个关键速度：

- **PP（Prompt Eval）**：处理输入 prompt 的速度（tokens/s），决定「首字前等多久」
- **TG（Token Gen）**：生成速度（tokens/s），决定「吐字快不快」

经验参考：Arm 服务器上 4B Q4 约 60 tok/s，Q8 约 37 tok/s；Apple Silicon 上 7B Q4_K_M 通常 40~60 tok/s。手机端侧小模型一般 15~30 tok/s。**真机 tok/s 比任何纸面推算都更该作为部署依据。**

### 4. 运行时还要观测哪些

部署后不是结束，要持续采集（和系列（二）的可观测性一脉相承）：

| 指标 | 含义 |
| --- | --- |
| 模型加载耗时 | 冷启动成本，决定是否常驻 |
| TTFT / PP 速度 | 首字延迟来源 |
| TG 速度（tok/s） | 流式体验 |
| 内存峰值 / KV 实际占用 | `--verbose` 看 `KV self size`，验证没超预算 |
| 是否真在 GPU offload | 防「偷偷 fallback CPU」 |
| 功耗 / 温升 / 掉电 | 端侧特有，决定能否持续 |
| 成功率 / 中断率 | 稳定性 |

把上面这些信息采集齐，就有了「这台设备能不能跑本地模型」的**客观依据**，而不是拍脑袋。

## 四、端侧 vs 云端：什么放端侧，什么放云端，标准是什么

这一节是问的核心。先给结论：**工程上绝大多数生产 App 是「混合」**——难点从来不是「二选一」，而是「这条请求该走端还是走云」。

### 1. 判断标准（五问法）

按这个顺序问，基本能定：

1. **装得下吗？** 权重 + KV cache + 开销 ≤ 设备可用内存？装不下 → **云**。
2. **隐私/离线是硬要求吗？** 数据不能出端、或必须弱网/离线可用 → **端侧优先**。
3. **量化后精度够吗？** 端侧小模型在目标任务上达到可接受准确率？不够 → **云**。
4. **高并发/多用户吗？** 要服务大量并发、摊薄成本 → **云**（服务端 GPU 连续批处理更划算）。单用户、交互式、偶发 → **端侧**更省（一次性算力，不按 token 计费）。
5. **功耗/发热可接受吗？** 移动端长时间推理会降频变慢、烫手掉电 → 撑不住就**回云端**。

> 这五条本质是四个维度：**内存可行性、隐私/延迟、精度、成本/并发**。前两条偏「必须端」，后两条偏「适合云」。

### 2. 决策表（场景 → 放哪）

| 场景 | 放端侧 / 云端 | 理由 |
| --- | --- | --- |
| 本地快捷指令、简单分类/改写 | **端侧** | 零网络、低延迟、逻辑简单 |
| 相册/短信/日历/剪贴板摘要 | **端侧** | 高敏数据不出端（合规） |
| 地铁/电梯里的基础问答 | **端侧（兜底）** | 离线可用 |
| 复杂推理、长上下文（100K+） | **云端** | 端侧装不下/精度不够 |
| 开放域问答、需要最新知识 | **云端** | 需联网 RAG / 最强模型 |
| 高并发服务多用户 | **云端** | 摊薄算力成本 |
| 需要频繁更新模型能力 | **云端** | 避免端侧下发大体积更新 |
| 意图初筛 / 路由判断 | **端侧** | 轻量、隐私、决定上不上云 |
| 复杂任务拆解与执行 | **云端** | 大模型规划 |

### 3. 混合部署的典型形态

```text
用户输入
  → 端侧小模型做意图初筛（快、隐私、零延迟）
       ├─ 简单/高敏 → 端侧直接处理（离线也能用）
       └─ 复杂/需联网 → 带上上下文上云大模型
                         └─ 云端结果回端渲染/落地执行
  → 弱网/云端超时 → 端侧小模型兜底（降级）
```

这和系列（一）（二）讲的「端云协同 + 分级路由 + 降级兜底」完全对得上。**端侧做初筛和保底，云端做上限**——这是当下最稳的架构。

### 4. 一个量化的「门槛」参考

给个粗略但可操作的阈值（以手机为例，桌面/ Mac 可放宽几倍）：

- 设备可用内存 < 模型权重 + KV(目标上下文) + 1GB 余量 → **不上端侧**
- 目标任务上，端侧量化模型准确率比云端低 > 5~10 个百分点 → **关键路径走云**
- 真机 TG < 15 tok/s 且任务是长文生成 → 考虑**回云端**或换更小模型
- 单次会话预估发热会触发降频 → **拆批 / 闲时跑 / 转云**

这些数字不是金科玉律，但能让人从「我觉得能跑」变成「我测过、算过、有依据」。

## 五、模型过大怎么办：断点续传与按需拆分下载

一个 2.5B 的模型量化后也往往有 1.5~2.6GB（Q4_K_M≈1.5GB，Q5_K_M≈2.1GB，Q6_K≈2.5GB，Q8≈2.6GB），那种 ~2GB 大概率是 Q5/Q6 档。在手机上这是实打实的空间与流量压力。解决「模型过大」，至少有四层手段，从易到难：

### 1. 第一杠杆：先把量化压到位（免费瘦身）

不碰下载和拆分，只换文件：

- 2.5B 从 Q8（2.6GB）降到 Q4_K_M（1.5GB），体积砍 40%，精度损失通常可接受。
- 先确认用的是「最小够用」的量化，再谈下载和拆分。这步是「零成本」的。

### 2. 断点续传：大文件下载的刚需（第 1 点）

2GB 在移动网络下必断，断点续传不是「锦上添花」而是「必须有」。原理是 HTTP 的 `Range` 请求：客户端记录已下字节，断线后用 `Range: bytes=已下-` 续传。

工程实现：

- **命令行 / 服务端拉取**：`curl -C -`、`wget -c` 原生续传；多连接加速用 `aria2c -x 16 -c`（16 连接 + 断点续传）；`huggingface-cli download`、`modelscope` 也都支持断点续传。
- **iOS App**：`URLSessionDownloadTask` 原生提供 `resumeData`，网络中断或 App 退后台后能用它恢复，不用自己管 Range 头。
- **Android**：`DownloadManager` 自带断点续传；或自管 `OkHttp` / `HttpURLConnection` 带 `Range` 头实现。

要点：

- **进度落盘**：已下字节 / 分片状态持久化，App 被杀后能恢复。
- **完整性校验**：下完做 hash / 文件大小校验，损坏只重下出错分片，别整体重来。
- **可暂停 / 可取消**：用户手动暂停后能从断点继续。

### 3. 文件分片下载（GGUF split）：把「一个大文件」拆成「多块并行下」

这回答了第 2 点的一种形态——但要先说清：**llama.cpp 的「拆分」是把同一个模型切成 N 个分片（shard），不是拆成「更简单的多个模型」**。

- 用 `llama-gguf-split` 把 GGUF 切成 `model-00001-of-00003.gguf` 这样的多个文件；推理时 llama.cpp 能**直接吃这组分片**（`llama_model_load_from_splits`），无需手动拼回。
- 价值在下载工程：分片可**并行下载 + 每片独立续传**，哪片断了只补哪片，不从头来；也规避某些文件系统 / 传输通道对单文件大小的限制。
- 但注意：**所有分片到齐才能加载运行**。这是「下载工程的拆分」，不是「能力拆分」。

> 补充一个相关点：llama.cpp 默认用 `mmap` 把模型文件映射进内存，只加载用到的页，所以**磁盘占用 ≠ 内存占用翻倍**；但移动端仍要同时留出磁盘空间和映射所需内存。可用 `--mlock` 锁内存防 swap，`--no-mmap` 则整体载入（更占内存、加载更慢）。

### 4. 真正「拆成简单模型、二次下载」：分层模型 + LoRA 适配器

第 2 点真正想做的——「先有一个能用的简单模型，后续再下更好的」——工程上叫**分层 / 渐进式模型交付（tiered / progressive model delivery）**，有两条成熟路线：

**(a) 分层模型（小模型先上，大模型后补）**

- 首发只下发 0.5B~1.5B 小模型：App 立刻可用、离线能跑基础能力。
- 后台 / Wi-Fi 下再「二次下载」更大的 3B/7B 作增强；检测到有大模型就优先用它，没有就降级用小模型。
- 这是系列（二）「弱网降级」的**反向操作**：先保证能用，再逐步变强。路由逻辑复用意图识别——简单意图走小模型，复杂意图等大模型就绪后走大模型。

**(b) 基座 + LoRA 适配器（把「能力」拆成小件按需下）**

- 下一份共享基座模型（如 3B），再用**很小的 LoRA 适配器**（通常几十 MB）挂载不同能力（翻译 / 摘要 / 代码 / 某领域）。
- llama.cpp 支持 `--lora FNAME`（可重复挂多个）和 `--lora-base FNAME`；基座只下一次，不同能力是「几十 MB 小包」，按需 / 按场景二次下载，几乎零痛感。
- 这是最贴合「拆成简单模型、后续二次下载」的做法：**能力被拆成可独立分发的小件**，而非把同一个大模型硬切。

**(c) MoE 稀疏加载（进阶）**

- Mixture-of-Experts 架构每 token 只激活部分专家，理论上可只加载活跃专家降本；但实践中整包仍多会整体下发，属进阶优化，不在「解决下载过大」的第一梯队。

### 5. 怎么选

- **只嫌下载慢 / 易断** → 断点续传 + GGUF 分片并行下载（第 2、3 点），模型本身不变。
- **想「先能用、后变强」** → 分层模型（小模型首发 + 大模型二次下载）。
- **想「一个基座、多能力按需扩展」** → 基座 + LoRA 适配器（能力拆小包）。
- **四者不冲突，可组合**：量化瘦身 + 分片续传下发 + 小模型首发兜底 + LoRA 扩展能力。

## 六、小结

回到开头的问题，逐条对齐：

- **llama 本地 run 为什么快**：纯 C/C++ 无 Python 开销、GGUF 单文件、量化原生、自动硬件探测、GPU offload 混合推理、KV 量化 + Flash Attention。
- **本地模型怎么配置**：先选量化（Q4_K_M 甜点）→ 定上下文（别贪大）→ 设线程和 GPU 卸载层数（`-ngl 99`）→ 开 Flash Attention → 用 `--verbose` 验证没偷偷 fallback。
- **内存/CPU 采集什么**：RAM 总/可用（最硬）、SoC/指令集、GPU/NPU 能力、存储、系统版本、温控；再用 `llama-bench` 真机测 PP/TG。核心是「权重 + KV cache 公式」算账。
- **端云分工标准**：五问法——装得下吗、隐私/离线硬要求吗、量化精度够吗、高并发吗、功耗可接受吗。本质是「内存可行性 × 隐私延迟 × 精度 × 成本并发」四个维度；工程上几乎都是「端侧初筛+保底、云端做上限」的混合。
- **模型过大怎么办**：量化瘦身 → 断点续传（HTTP Range / `URLSession` resumeData / `aria2c`）→ GGUF 分片并行下载（`llama-gguf-split`）→ 分层模型（小模型首发、大模型二次下载）→ 基座+LoRA 适配器（能力拆小包按需下）。四者不冲突，可组合。

这一篇把「本地模型怎么落地」讲透了。它和系列（一）的链路、（二）的体验优化是配套的：**（一）知道要端云协同，（二）知道怎么把体验做好，这一篇知道怎么把模型真正跑在端上、并拿数据决定边界在哪**。

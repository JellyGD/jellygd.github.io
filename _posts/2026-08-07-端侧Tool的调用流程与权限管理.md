第一次在 iOS 上让本地小模型调工具，用户只问「今天给宝宝吃什么」，它一口气吐了三个 tool_call——一个参数空着，另一个 category 写成「随便」。前端照单全收，界面直接崩了。

那次之后我认准一件事：端侧的 Tool 不是给模型递个函数指针，而是一份契约。模型按契约格式「下单」，App 验货、执行、回灌。把本地模型想成塞进 App 的解码内核，Tool 就是插进 App 的解码器插件，契约就是插件接口的规格书。

## 契约先分两类

这份契约先分两类，区别在「真理在哪」：

- **展示型工具**：模型把结构化数据写进 arguments，前端直接渲染，没有副作用。真理在模型写出的 JSON 里（比如 `present_baby_foods`）。
- **执行型工具**：模型输出「我想创建提醒」的意图，App 真正去建一条本地通知，再把「建好了 / 失败了」回灌给模型接话。真理在 App 跑完的回灌结果里（比如 `create_local_reminder`）。

## 运行时调用流：五步，闸门卡在执行前

契约定下来，真正的考验在运行时：一个 tool_call 从模型嘴里出来到落地，中间怎么走。我把它拆成五步，权限闸门卡在「执行之前」：

![端侧 Tool 运行时调用流](/assets/images/tool-runtime-call-flow.svg)

1. 模型不是一次性给完整 JSON，而是按 chunk 吐 `tool_calls`，name 和 arguments 分开流，arguments 还可能被切成几片。
2. AgentLoop 按 index 把碎片拼起来，流结束才 `JSON.parse`。index 非法（不是非负整数、溢出）直接丢，不硬塞——这步是「连传输层都不能信」。
3. 拿 name 去 ToolRegistry 查定义。查不到？这 tool 不存在，回灌报错让模型换一个。
4. 权限闸门——端侧和云端最大的差别，下面单独讲。
5. 过了闸门才执行：本地代码直接跑，要联网的经 MCP 走到云端 Server。结果包成 `role:tool` 回灌，模型接着决策；`finish_reason=stop` 才把话给用户。

一个反直觉点：权限校验和参数校验都发生在执行之前，不是在 schema 里声明就算数。schema 只是给模型看的说明书，真正的门是运行时这道闸。

## 怎么设计一个 Tool

那具体怎么设计一个 tool？我把它拆成两份契约绑在一起：一份给模型看，一份给运行时看。

![一个 Tool 的构成](/assets/images/tool-composition.svg)

模型侧契约就两样：能力描述（name + description，写清它干什么、不干什么）和参数 Schema（类型、必填、枚举、取值范围）。这是给模型看的说明书，决定它会不会「叫对号」。

运行时契约是真正的落点，四样：权限画像（PermissionPolicy）、执行体（本地代码或经 MCP 调云端）、校验器（parseArguments 强校验）、回灌器（成功和失败都回灌 `role:tool`）。少一样，这个 tool 在端侧都跑不稳。

## 权限怎么定：声明基线，闸门终局

现在回答最关键的问题：二次确认是不是定义时就定死？

我的判断——声明定的是「基线档位」，不是「终局裁决」。tier（auto / confirm / explicit）是能力的固有属性，跟这次传什么参数无关：「建提醒」永远是写动作，天然该 confirm；「推荐辅食」永远是只读渲染，天然该 auto。写在定义里没问题，这是声明。

真正的门是运行时这道闸，它在声明之上再叠加上下文做最终裁决。先按风险分三档：

![端侧权限分级与端侧否决权](/assets/images/tool-permission-tiers.svg)

- **自动执行**：读本地状态、展示型渲染。无副作用，端侧自己拍板，不打扰用户。
- **需确认**：写本地数据（建提醒、发通知）。会留痕迹，执行前弹确认，且最好可撤销。
- **显式授权 / 禁止**：发消息、扣费、删数据、上传隐私。一旦执行难回头，必须用户一次性显式授权；涉及上传隐私的，端侧直接禁止，云端想调也调不动。

最关键的在底下那条：端侧否决权。云端下发的 tool 意图，端侧不是照单全收——它按本地策略做最终裁决。云端让模型去读用户健康数据上传，端侧直接拦下，回灌「无权限」。这也是端云结合里「本地 tool 绝不上云」是硬规矩的原因：执行权在端，不在云。

还有一层容易被忽略：iOS 原生的能力门控。摄像头、相册、位置这些系统权限，tool 执行前得先查 `AVCaptureDevice` / `PHPhotoLibrary` 的授权状态——模型不知道用户没给相册权限，端侧得替它查，没授权就走降级或回灌报错。

闸门到底怎么裁决？看这张图，它按顺序叠了五件事：

![权限闸门决策流](/assets/images/tool-permission-gate.svg)

1. 取声明画像（default tier / scope / data）。
2. 执行目标 + 敏感数据：标了 local-only 的工具这次却被路由去联网？直接拦。触碰健康 / 隐私且要走网络？直接禁。
3. 用户授权状态：之前授过权且覆盖当前上下文？放行（会话级或永久）。
4. 原生门控 + 频率护栏：要摄像头 / 相册但没给授权？拦。同一个 safe 工具被连环调几百次？升成 confirm。
5. 按声明 tier 终裁：auto 放行、confirm 弹确认、explicit 要一次性显式授权。

## 用代码落地

用代码表达就是——定义里挂一个 PermissionPolicy，闸门里一个 decide() 综合声明和上下文：

```swift
enum ToolTier { case auto, confirm, explicit }
enum SideEffect { case read, writeLocal, writeRemote, destructive }
enum CapabilityScope { case localOnly, network }
enum DataCategory { case none, health, location, pii }

struct PermissionPolicy {
    let tier: ToolTier          // 定义时定下的基线档位
    let sideEffect: SideEffect  // 这个能力本身有没有副作用
    let scope: CapabilityScope  // 能不能碰网络
    let touches: [DataCategory] // 会碰哪些敏感数据
}

enum Decision { case allow, prompt, block }

func decide(_ tool: Tool, ctx: RuntimeContext) -> Decision {
    let p = tool.policy
    // 1. 执行目标：本地工具被路由到云端 → 拦截
    if p.scope == .localOnly && ctx.wouldHitNetwork { return .block }
    // 2. 敏感数据：触 health/pii 且走网络 → 禁止
    if p.touches.contains(.health) && ctx.wouldHitNetwork { return .block }
    // 3. 用户授权状态（会话级 / 永久）
    if let g = ctx.consentStore.grant(for: tool.name), g.covers(ctx) { return .allow }
    // 4. 原生能力门控
    if p.needsNativeAuth && !ctx.nativeAuthGranted { return .block }
    // 5. 频率护栏
    if ctx.callCount(tool.name) > p.rateLimit { return .prompt }
    // 6. 按声明 tier 终裁
    switch p.tier {
    case .auto: return .allow
    case .confirm: return .prompt
    case .explicit: return ctx.explicitGrant ? .allow : .prompt
    }
}
```

代码里 `tier` 是声明、`decide()` 是闸门，二者分工就是「声明定基线，闸门定终局」。

## 回到辅食 App 的真实样板

落到辅食 App 看就很清楚：`present_baby_foods` 的 policy 是 auto（展示型、只读），`create_local_reminder` 是 confirm（写本地通知、可撤销），任何「上传宝宝过敏数据」的意图 policy 是 block（端侧禁止、本地优先）。`BabyFoodTool.parseArguments:` 里做的枚举白名单、`fire_at` 必须晚于 now，干的就是闸门里校验器的活儿。

端侧 Tool 这套东西，我反复踩坑才摸清：声明定基线，闸门定终局。定义时把能力的风险画像写清楚，运行时把「凭什么能走」的裁决做全——模型是解码内核，不是守规矩的同事，安全得靠 App 自己兜底。
